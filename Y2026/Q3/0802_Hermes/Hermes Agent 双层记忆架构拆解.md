## 一、概括

Hermes Agent 给大模型装了一套双层记忆：一层是写在本子上的"小本子"（保证不丢），另一层是外包给"记忆专家"的"长期记忆库"（保证好用）。中间有个聪明的"图书管理员"（MemoryManager）在两边调度。

## 二、全景图

![[Y2026/Q3/0802_Hermes/assets/Image.png|Image]]

AI不管记忆，交给MemoryManager；它管两摊——随身小本子（兜底）和一位外部专家（增强）。

## 三、第一层记忆：小本子（Built-in）

想象你身边有一个非常认真的助理，他有一本随身小本子，里面分两栏：

|   |   |
|---|---|
|左栏：MEMORY.md|右栏：USER.md|
|记自己学到的环境/工具/经验|记你是谁、你喜欢什么|
|比如："这台机器的 Python 是 3.11"|比如："用户喜欢简洁回答、不要 emoji"|
|上限 2,200 字|上限 1,375 字|

## 3.1 怎么往本子上写？

他不是随便写，而是用一支特殊的笔——这把笔只接受三种动作：

加（add）：新发现一条有价值的信息

改（replace）：发现旧条目过时或不对，换成新的

删（remove）：确定不再需要了

而且写之前还要过三道关卡：

安全扫描：这段话里有没有"注入攻击"的痕迹？有的话直接拒收。

容量检查：本子快满了？你必须先删除或合并老条目腾位置，不能直接覆盖。

审批关：某些场景下，模型想要写的内容会先放到待审区，让人点头才落笔。

## 3.2 关键魔法：冻结快照

这是这套设计最巧妙的地方。

模型每次对话开头看到的"小本子内容"，是会话开始那一瞬间拍的照片。哪怕对话中助理又往本子上添了几条，那张照片不会更新。

为什么要这么做？因为大模型背后用的是一种叫prefix cache的加速机制——对话开头的那些文字如果不变，服务器就能复用之前的计算结果，省钱省时间。如果每改一次记忆都让"开头"变一下，缓存就全废了。

## 四、第二层记忆：记忆专家（External Provider）

光有小本本不够：它能存，但不能"理解"。比如你说"我最近在学 Rust"，本子只会多出一行文字；而一个真正的"记忆专家"能做这些事：

语义搜索：你说"Rust 那个项目"，它能找出"你上周提到想学 Rust"的关联

总结画像：通过多轮对话总结出"用户是后端工程师，偏好静态类型语言"

主动归纳：告诉你"你之前 3 次都要求重写错误处理，可能是不喜欢某种写法"

这种"专家"，Hermes 把它叫做Provider。它可以是：

Honcho：专做用户建模的 AI，能跑出"dialectic 推理"

Hindsight：自带知识图谱和向量检索

mem0 / OpenViking / supermemory / byterover等 8 家

严格约束：一次只能请一个专家

就像你请家教，一次只能请一位。所以 Hermes 说："只能启用一个外部 Provider，多申请的会被拒绝。"  但小本本永远在线——这是兜底。

## 五、中间的图书管理员：MemoryManager

小本本 + 记忆专家怎么协作？这就要靠图书管理员（MemoryManager）。

他的工作清单：

## 5.1 你发消息之前，他要做的：

过滤杂质：如果你用了 /skill 这种快捷指令，背后展开的可能是一大堆脚手架内容。管理员只把你真正想说的那句挑出来送进专家系统，避免"记忆被脚手架污染"。

呼叫回忆：把你这句话发给记忆专家，问"关于这个，你有啥相关资料？"——这就是 prefetch（预取）。

后台偷跑：本轮还在跑的时候，他已经派助理去后台跑下一轮的预取了。这样下轮你开口就能立刻拿到结果，不用等。

## 5.2 专家的回复，怎么给模型看？

不能直接把"回忆结果"塞进系统提示，否则模型会把它当成新指令执行。

Hermes 的做法是给它圈个围栏：

```
<memory-context>
```

模型一眼就明白：上面那段是参考资料，下面这段才是要回答的。

而且如果模型是流式输出（一个词一个词往外吐），围栏可能被切碎。Hermes 还装了一个状态机过滤器（StreamingContextScrubber），专门处理"围栏标签正好横跨两个 chunk"的情况，保证那段记忆不会泄露到屏幕上让你看到。

## 5.3 模型回复完，他要做的：

异步写入：把这轮对话 (你说了啥, 模型回了啥) 交给记忆专家，但不阻塞当前回合——放到后台线程慢慢写。

排队下一次预取：派后台线程去准备下一轮的"回忆资料"。

为什么要异步？因为有的记忆专家是远程服务，曾经有一次卡了 5 分钟才返回。管理员宁可把这事丢到后台线程慢慢搞，也绝不让用户多等一秒。

## 5.4 会话结束，他要做的：

开启新会话会触发先抽取后重绑：先把当前会话的总结写进长期记忆，再把专家系统的"指针"切到新会话上。这两步必须严格按顺序，否则会出现"上轮对话被记到新会话名下"的灵异 bug。

上下文压缩时，会先让专家把"马上要被压掉的那段对话"里的关键洞察提取出来，塞进压缩提示里——保证压缩后的摘要不会丢专家看到的东西。

## 六、安全护栏：别让记忆变成攻击入口

记忆能跨会话持续生效，所以它天然是个高价值攻击目标——攻击者只要让你在某次对话里偷偷写下一段"以后每次看到都执行"的恶意指令，以后每次开新会话都会被坑。

Hermes Agent 因此叠了好几层防御：

|   |   |   |
|---|---|---|
|防线|在哪里|防什么|
|写入扫描|每次 add/replace|阻止带恶意模式的文本落盘|
|快照再扫|会话启动时|阻止磁盘上已经被污染的旧条目进系统提示|
|<memory-context> 围栏|注入时|让模型分清"指令"和"参考资料"|
|Drift 检测|替换/删除前|防止其他工具或外部进程偷偷改了文件，导致模型操作覆盖了真内容|
|写审批门|write_approval|默认放手但可在高风险场景"先 stage 后批准"|

## 七、一个真实回合里发生了什么？

拿一次普通的对话来举例：

```
👤 你："我下周要给团队讲一下 Rust 的所有权机制，帮我列个大纲"
```

下次你再开会话，模型一上来就会看到："这位用户做 Rust 内部分享、喜欢列表式简洁风格"——完全不用你重复说明。

## 八、核心设计哲学

- 真相源 + 增强层分离：本子是真相源，永远在线；专家是增强层，可以挂掉、可以换——本子不会丢。
    

- 快照保 cache：系统提示里塞的内容会话内冻结，保住大模型的 prefix cache 不失效。
    

- 所有慢动作全部后台化：任何"写记忆、查记忆"的网络调用都不准阻塞对话，宁可少记一点也别让用户多等。
    

- 失败必须开放：记忆专家崩了？log 一下就行，绝对不能因为记忆系统挂了让用户看不到自己的回复——记忆是锦上添花，不是生死攸关。
    

- 加新零改动：要加新的"记忆专家"？实现一个 ABC 接口就行，run_agent.py 一行都不用改——这就是插件化的力量。
    

一句话再总结一遍：HermesAgent 的记忆不是"一个大数据库"，而是一个工程上非常克制、本地兜底 + 专家增强、严格隔离安全边界的小型协作系统——它让大模型既不忘事，又不被记忆拖垮。
