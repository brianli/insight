# K3 Native Vision 深入解析

## 核心结论

K3 的 **Native Vision** 不是简单地给语言模型外挂一个视觉编码器，而是把视觉变成与语言共同训练、共同进入同一上下文、共同服务于 `next-token prediction` 的信息通道。

它的核心变化有三层：

1. **训练范式变化**：从 `SigLIP 视觉预训练 → 对齐 → 接入 LLM`，转向 MoonViT-V2 与语言模型从零联合训练；
2. **优化目标变化**：从偏全局语义对齐的 `contrastive learning`，转向直接服务语言生成、OCR、布局理解、视觉代码和 Agent 反馈的 `next-token prediction`；
3. **视觉计算路径变化**：通过空间/时间 Attention 分解、时间池化、2×2 `pixel shuffle` 压缩视觉 token，适配 1M-token 上下文和视频输入。

一句话：

> **K3 不是把视觉模型接到语言模型旁边，而是让视觉从训练第一天起就成为语言模型的感知、生成、行动和验证通道。**

## 多模态对 K3 意味着什么

### 1. 多模态不是“支持图片输入”，而是扩大模型的世界接口

如果模型只处理文本，它接触到的是已经被人类语言化、摘要化、解释过的世界：

```text
现实世界 → 人类观察与描述 → 文本 → 模型
```

多模态 K3 则可以直接接触更多原始状态：

```text
文本、图片、视频、网页、图表、屏幕、渲染结果
                         ↓
                  统一表示与上下文
                         ↓
                 推理、生成、调用工具
```

所以多模态的本质不是增加一个输入格式，而是把模型从“处理语言”推进到“处理世界状态”。

对 K3 而言，视觉至少承担三种角色：

1. **感知输入**：读取图像、视频、网页、图表、屏幕和文档；
2. **中间状态**：保存 Agent 执行过程中的截图、渲染结果和环境反馈；
3. **验证信号**：判断代码生成的网页、图形或视觉产物是否真正达标。

### 2. 多模态补上了 Agent 闭环中最关键的“观察—验证”环节

K3 的目标不是只回答问题，而是完成长时任务。一个真实 Agent 的基本循环是：

```text
理解目标
  ↓
制定计划
  ↓
调用工具或修改环境
  ↓
观察新的状态
  ↓
验证结果
  ↓
纠错并继续行动
```

如果只有文本，模型只能依赖工具返回的文字描述；但现实中的大量状态并不是天然文本：

- 网页是否真的渲染正确；
- 按钮是否出现在目标位置；
- 图表中的异常点在哪里；
- CAD 结构是否符合要求；
- 游戏画面发生了什么；
- 视频中的动作是否完成；
- 代码生成的 SVG 或 3D 场景是否视觉上正确。

多模态让模型可以直接读取这些状态，并把视觉反馈重新放回同一个上下文。因此，K3 的视觉能力不是旁路能力，而是 Agent 闭环中的：

> **观察器 + 验证器 + 环境反馈接口。**

### 3. 对 K3 而言，多模态与 1M 上下文是耦合的

K3 的 1M-token context 不只是为了读一篇更长的文档，也可以承载长时 Agent 轨迹：

```text
任务要求
  + 历史文本
  + 工具调用
  + 中间代码
  + 页面截图
  + 视频帧
  + 执行日志
  + 修订结果
  + 验证反馈
```

如果这些视觉状态必须由独立模型处理后再压成几句文字，信息会在跨模型摘要过程中丢失。Native Vision 让视觉特征经过 projector 进入共享 embedding space，与文本和代码一起留在同一条上下文链上。

因此，K3 的三个架构维度可以这样理解：

| 维度 | K3 机制 | 解决的问题 |
| --- | --- | --- |
| 序列长度 | KDA + Gated MLA | 如何保存和检索百万 token 的历史 |
| 网络深度 | AttnRes | 如何跨层选择性读取历史表示 |
| 模型宽度 | Stable LatentMoE | 如何扩大条件专家容量 |
| 世界接口 | Native Vision | 如何把视觉状态纳入推理和行动闭环 |

多模态不是前三个维度之外的装饰，而是让这些计算能力接触真实环境状态的接口。

### 4. 视觉使“代码生成”从文本正确变成结果正确

文本模型生成代码时，通常只能依据：

```text
代码语法
单元测试
文本日志
```

但很多任务的正确性最终体现在视觉结果：

- 网页布局；
- UI 交互；
- SVG 图形；
- 3D 场景；
- 数据可视化；
- 游戏画面；
- CAD 图纸。

K3 将代码与渲染结果放进同一个训练和交互闭环：

```text
生成 HTML/CSS/SVG/代码
          ↓
浏览器或渲染器执行
          ↓
截图或视频反馈
          ↓
模型比较目标与结果
          ↓
修改代码
```

这改变了“正确”的定义：

- 文本模型更容易优化“代码看起来合理”；
- 多模态 Agent 可以进一步优化“程序运行后结果正确”。

因此，视觉是 K3 Web development、视觉 Agent 和多步工具使用能力的重要反馈源，而不只是一个额外 benchmark 模态。

### 5. 多模态降低了语言描述这一层的信息损失

把视觉状态先转换成文本再交给语言模型，会发生不可逆的信息压缩：

```text
原始截图/视频
      ↓
视觉模型摘要
      ↓
“页面上有一个按钮”
      ↓
语言模型决策
```

摘要可能丢掉：

- 精确坐标；
- 字体和间距；
- 局部异常；
- 颜色差异；
- 物体之间的空间关系；
- 帧间变化；
- 视觉上但难以 verbalize 的结构。

K3 使用视觉 token、坐标监督、代码—渲染配对和统一上下文，尽量让这些信息直接参与生成。它仍然会压缩视觉 token，但压缩发生在模型内部的表示层，而不是先由外部模型做一次不可逆的自然语言摘要。

### 6. 多模态让模型学习“跨模态约束”

K3 的强项不只是分别看懂图片、分别读懂文本，而是学习不同模态之间的对应关系：

| 跨模态关系 | 例子 |
| --- | --- |
| 图像 ↔ 文本 | OCR、图表问答、文档理解 |
| 图像 ↔ 坐标 | 点击、定位、GUI 操作 |
| 视频 ↔ 时间 | 动作过程、状态变化、事件顺序 |
| 代码 ↔ 渲染结果 | 网页、SVG、3D、游戏 |
| 视觉状态 ↔ 工具动作 | 看截图后选择下一步操作 |
| 目标描述 ↔ 视觉结果 | 判断生成物是否满足需求 |

这些约束比单模态识别更接近现实任务。模型真正需要回答的不是“图中有什么”，而是：

> **看到这个状态后，我下一步应该做什么；做完以后，怎样判断是否成功。**

## 为什么 K3 要做多模态

这里的“一定”需要校准：**多模态不是所有语言模型都必须具备的能力，但对 K3 想成为通用长时 Agent，它几乎是战略必选项。**

### 1. 因为 K3 的目标已经超出文本问答

如果目标只是：

- 文本续写；
- 文本摘要；
- 纯文本知识问答；
- 代码补全；

多模态不是必要条件，做多模态反而会增加数据、算力、训练和部署成本。

但 K3 的目标包括：

- 长时编码 Agent；
- Web development；
- vision-in-the-loop；
- 多步专业工作；
- 屏幕和环境交互；
- 视觉推理；
- 生成后反复验证。

这些任务的环境状态天然包含图像、视频、网页和渲染结果。没有多模态，模型只能依赖外部系统把世界翻译成文本，能力上限会被翻译器限制。

### 2. 因为真实世界不是文本接口

文本是人类与模型交互的方便接口，不是现实世界的完整接口。

模型如果只能处理文本，面对真实环境时会遇到一个结构性瓶颈：

```text
环境状态
    ↓
外部系统描述状态
    ↓
语言模型推理
    ↓
外部系统执行动作
```

每一次“描述状态”都可能丢信息，且描述质量受外部模型和固定 schema 限制。

多模态 K3 可以缩短链路：

```text
环境视觉状态
      ↓
K3 直接感知
      ↓
推理与动作
      ↓
新的视觉状态
```

这不是为了追求模态数量，而是为了减少世界状态到语言之间的转换损失。

### 3. 因为视觉提供独立于语言的验证信号

纯文本任务中，模型很容易在语言空间里自洽，却与外部现实不一致。视觉和执行结果提供了额外约束：

- 页面是否真的显示正确；
- 图表数值和形状是否匹配；
- 生成的结构是否符合目标；
- 操作是否落在正确位置；
- 视觉结果是否与代码对应。

这种信号可以帮助 Agent 发现“语言上说得通、结果上不正确”的错误。

要注意：多模态**降低**验证盲区，不会自动消除幻觉；模型仍可能误读图像、忽略细节或错误解释视觉反馈。

### 4. 因为图像和视频是长时任务的状态记忆

K3 的 long-horizon RL 轨迹可能包含数百或数千次工具调用。视觉观察不是一次性的输入，而是任务状态的一部分：

```text
第 1 次截图：初始页面
第 2 次截图：第一次修改后
第 3 次截图：修复布局后
第 4 次截图：交互测试后
...
```

如果只保留文本摘要，模型难以回看视觉细节；如果视觉信息进入统一上下文，就能与同一轨迹中的代码、工具调用和文字推理共同被检索。

这也是 KDA、Gated MLA 和 Native Vision之间的协同点：

- KDA 高效处理大部分长序列混合；
- Gated MLA 周期性保留精确全局检索；
- Native Vision 把视觉轨迹纳入这条长序列。

### 5. 因为多模态扩大训练数据的结构，而不只是扩大数据量

同一个任务可以产生多种互相约束的表示：

```text
自然语言需求
    ↔ 代码
    ↔ 截图
    ↔ 坐标
    ↔ 视频过程
    ↔ 执行结果
```

这比单纯增加更多文本有更强的结构监督。模型不仅学习“答案是什么”，还学习：

- 语言需求如何对应代码；
- 代码如何产生视觉结果；
- 视觉结果如何对应坐标和动作；
- 动作如何改变环境；
- 环境反馈如何驱动修正。

这对 Agent 能力尤其重要，因为 Agent 的能力不是单次预测，而是从状态到动作再到新状态的映射。

## 为什么不能简单用独立视觉模型替代

独立视觉模型并不是不能用，但它会引入四个接口问题：

1. **信息瓶颈**：视觉模型必须把丰富状态压成 embedding 或文字摘要；
2. **上下文割裂**：语言模型难以直接回看原始视觉细节；
3. **错误累积**：视觉识别错一次，语言决策会在错误状态上继续推理；
4. **反馈延迟**：多模型调用增加系统延迟和调度复杂度。

K3 的 Native Vision 选择共享 backbone 和统一 token stream，目标是让：

```text
视觉观察、语言推理、代码生成、工具反馈
```

在同一模型状态中连续发生。

但这不是绝对优于模块化系统。独立视觉模型仍然可能在以下场景更合适：

- 专业视觉检测；
- 低延迟视觉前端；
- 隐私隔离；
- 独立升级视觉模型；
- 视觉任务与语言任务完全解耦。

K3 选择统一多模态，是因为它优先优化的是**通用 Agent 的端到端闭环**，而不是单项视觉模块的最优性。

## 多模态的代价与 K3 的应对

多模态不是免费能力。它带来：

| 代价 | 具体问题 | K3 的应对 |
| --- | --- | --- |
| 计算成本 | ViT、视频时空 Attention 很重 | 空间/时间分解、Temporal Pooling |
| 上下文成本 | 图像和视频产生大量 token | 2×2 `pixel shuffle`、视觉 token 压缩 |
| 训练稳定性 | 视觉塔与 LLM 梯度冲突 | 从零联合训练、RMSNorm、去 bias |
| 负载波动 | 大图和长视频计算量差异很大 | Dynamic CP、视觉 encoder 优化 |
| 数据成本 | 需要图文、视频、坐标、代码—渲染数据 | 扩大程序化多模态数据 |
| 目标冲突 | 全局语义、OCR、空间、语言生成目标不同 | 统一 next-token prediction 与任务数据 |

技术报告明确指出，3T 级原生多模态训练会带来三类系统问题：

1. Expert Parallel 各 rank 的 token 负载不均；
2. activation、gradient 和 optimizer state 超出显存预算；
3. 视觉编码器的可变计算暴露在关键路径上。

这说明多模态对 K3 不只是模型架构问题，也反向定义了 MoonEP、memory-efficient training 和 multimodal encoder optimization 的系统需求。

## 最重要的判断：多模态是 K3 的“世界接口”

可以把 K3 看成四层：

```text
KDA + Gated MLA
    → 处理更长的序列

AttnRes
    → 在更深的网络中访问历史层

Stable LatentMoE
    → 提供更大的条件模型容量

Native Vision
    → 把真实视觉状态接入模型
```

前三者主要扩展模型的**计算能力**；Native Vision 扩展的是模型能够观察和操作的**世界范围**。

因此，K3 的多模态战略不是“多支持一种输入格式”，而是从：

```text
语言模型：预测下一段文字
```

走向：

```text
通用 Agent：观察环境 → 预测动作/代码 → 执行 → 读取反馈 → 修正
```

## 边界：不是“必须多模态”，而是“目标决定是否必须”

| 目标 | 多模态是否必要 |
| --- | --- |
| 纯文本聊天 | 不必要 |
| 文本摘要与翻译 | 不必要 |
| 代码补全 | 通常不必要 |
| 图表、文档、OCR | 必要 |
| GUI/Web Agent | 基本必要 |
| 视频理解与交互 | 必要 |
| 视觉代码生成与验证 | 基本必要 |
| 通用长时 Agent | 战略上接近必要 |

所以最准确的结论是：

> **多模态不是大模型的普遍必修课；但如果模型要从“语言预测器”升级为能在真实环境中观察、行动、验证和修正的通用 Agent，多模态就不再是附加功能，而是基础接口。**

## Native Vision 的具体设计

### 1.1 视觉、文本、视频进入同一个上下文

K3 的路径不是：

```text
图片 → 独立视觉模型 → 图片描述/视觉向量 → 语言模型
```

而是：

```text
文本 token
图片 token
文本 token
视频 token
代码 token
截图 token
    │
    ▼
同一个 K3 backbone
```

视觉输入首先经过 `MoonViT-V2` 编码，再通过轻量级 MLP projector 映射到语言模型的 hidden space，之后与文本 token 一起进入共享主干。

`Native` 不意味着没有视觉编码器或 projector，而是：

> **视觉编码器、projector 和语言 backbone 从预训练开始就作为一个统一系统共同优化，而不是先分别训练、之后再做 post-hoc alignment。**

因此模型可以形成这样的闭环：

```text
看截图 → 写代码 → 渲染页面 → 再看截图 → 修改代码
```

它不需要在独立视觉模型、语言模型和外部工具之间来回切换表示空间。

### 1.2 MoonViT-V2 改为从零训练

K3 相比过去最显著的变化是：

```text
过去：
SigLIP 初始化 MoonViT-3D
        ↓
接入语言模型
        ↓
联合训练或模态对齐

K3：
随机初始化 MoonViT-V2
        ↓
与语言模型共同进行 next-token prediction
```

报告给出的直接观察是：

- `SigLIP` 初始化的 `MoonViT-3D` 梯度范数更高；
- 训练过程中存在频繁梯度尖峰；
- 从零训练的 `MoonViT-V2` 梯度更低、更平滑；
- `MoonViT-V2` 在视觉评测上可以匹配 `SigLIP` 初始化基线。

图 6 的重点是**优化稳定性**，不是简单宣布“从零训练在任何场景都优于 SigLIP”。

### 1.3 MoonViT-V2 的架构与系统设计

MoonViT-V2 继承了 K2.5 视觉路径的基本骨架：

- 27 层 Vision Transformer；
- 约 0.4B 参数；
- 图像和视频共享视觉参数；
- 视觉输出经过轻量 MLP projector 接入语言模型。

围绕从零联合训练和超长上下文，K3 使用了：

- `RMSNorm`；
- 去掉线性层和 Attention 投影的 bias；
- 帧内空间 Attention 与帧间时间 Attention 分解；
- 时间维度 pooling；
- 2×2 `pixel shuffle`，将视觉 token 数量压缩四倍。

### 1.4 视觉数据从图片描述扩展到 Agent 场景

K3 的视觉数据不只是传统的 image-caption pair，还包括：

- image-text interleaving；
- OCR；
- visual perception；
- video；
- visual coding；
- 绝对坐标和归一化坐标；
- SVG；
- 3D asset；
- Webpage；
- Game；
- CAD；
- 代码与渲染视觉结果配对。

这说明目标已经从“识别图片内容”转向：

> **视觉理解 + 代码生成 + 工具执行 + 视觉验证。**

## MoonViT-V2：为什么放弃 SigLIP 初始化

### 2.1 两种训练目标不完全一致

`SigLIP` 的核心目标是图像—文本对比学习，抽象为：

$$
\operatorname{sim}(v_{\text{image}},t_{\text{text}})
$$

对于匹配的图像和文本更高，对于不匹配的组合更低。它主要优化：

- 图像和文本的全局语义对应；
- 图像级概念识别；
- “这张图是什么”。

K3 的主目标是多模态 `next-token prediction`：

$$
\mathcal{L}_{\text{LM}}
=
-\sum_t\log p(x_{t+1}\mid x_{\leq t},v)
$$

它要求视觉表示支持：

- OCR；
- 视觉问答；
- 坐标定位；
- 代码生成；
- 屏幕理解；
- 多轮视觉反馈；
- 长上下文中的跨模态检索。

两者的优化重点不同：

| `SigLIP` 对比学习 | K3 Native Vision |
| --- | --- |
| 图像级、全局语义 | token 级、任务相关细节 |
| 图像与文本是否匹配 | 看到视觉后下一步生成什么 |
| 强调模态间几何对齐 | 强调视觉表示对语言生成的可用性 |
| 适合通用视觉语义 | 适合统一多模态 Agent |

因此，`SigLIP` 的表示空间不一定是 K3 语言生成最需要的空间。

### 2.2 预训练视觉表示与 LLM 表示存在接口冲突

`SigLIP` 预训练后已经形成了一套自己的表示几何，包括：

- 激活尺度；
- 特征方向；
- 语义聚类方式；
- 层间信息分布；
- 梯度统计。

接入语言模型后，视觉输出要经过 projector 进入 LLM：

```text
SigLIP 视觉表示空间
        ↓
      Projector
        ↓
LLM 语言生成表示空间
```

这个 projector 不仅要做尺度转换，还要完成：

- 表示空间旋转；
- 视觉细节重编码；
- 与语言 hidden state 对齐；
- 适应不断变化的联合训练梯度。

**报告直接验证的事实**是：`SigLIP` 初始化版本的 vision tower 梯度更高、尖峰更多。

**机制上的合理推断**是：预训练视觉表示在接入联合语言训练后需要被大幅重新塑形，而从零训练没有这么强的“旧表示—新目标”冲突。

### 2.3 从零训练让视觉表示直接服务语言目标

从零训练并不等于没有先验，而是让视觉编码器从第一步就接受语言模型损失的塑形。

过去的路径是：

```text
先学“图片是什么”
        ↓
再学“怎么把图片交给语言模型”
```

K3 的路径是：

```text
直接学习什么视觉信息能帮助模型预测下一个 token
```

例如输入网页截图并要求修改 HTML，真正有用的视觉信息不仅是“这是一张网页”，还包括：

- 按钮的位置；
- 文本内容；
- 页面布局；
- 颜色和边界；
- 视觉结构与代码结构的对应关系；
- 修改前后的差异。

`next-token prediction` 会直接奖励这些对生成有用的视觉特征。

## MoonViT-V2 的稳定化设计：RMSNorm 与无 bias

### 3.1 RMSNorm：控制多模态激活尺度

RMSNorm 可以抽象为：

$$
\operatorname{RMSNorm}(x)
=
\frac{x}{\sqrt{\operatorname{mean}(x^2)+\epsilon}}
\odot g
$$

联合训练中，不同模态的输入统计差异很大：

- 文本 token 是离散 embedding；
- 图像 patch 是连续高维特征；
- 视频还引入时间维度；
- 视觉序列长度随分辨率和帧数变化。

RMSNorm 主要减少：

- 层间激活尺度漂移；
- 图像和视频输入的幅值差异；
- projector 前后表示幅值不一致；
- 多模态联合训练中的梯度放大。

它解决的是**优化尺度问题**，不是语义对齐问题。

### 3.2 去掉 bias：降低可累积的偏移

普通线性投影为：

$$
y=Wx+b
$$

K3 在视觉塔的线性层和 Attention 投影中去掉 bias：

$$
y=Wx
$$

合理的机制解释是：

- 避免每层引入额外的可学习均值偏移；
- 减少从零训练时的参数自由度；
- 降低深层视觉塔中的 activation drift；
- 简化视觉塔与语言主干之间的统计接口。

需要区分事实和推断：技术报告明确指出这种设计有助于从零优化稳定，但没有给出“单独去掉 bias”的独立消融结果，因此上面的具体机制属于合理推断。

## 图像与视频的统一编码

图像和视频共享大量底层视觉结构：

- 边缘；
- 纹理；
- 物体；
- 文字；
- 局部结构；
- 空间布局。

视频新增的核心因素主要是时间关系：

- 运动；
- 顺序；
- 状态变化；
- 帧间因果；
- 动作过程。

因此更合理的分工是：

```text
共享空间视觉编码
        +
时间维度建模
```

而不是维护两套完全独立的视觉编码器。

参数共享可以带来：

- 参数复用；
- 图像数据与视频数据共同训练；
- 图像能力迁移到视频；
- 视频动态信息反过来帮助理解过程；
- 图像与视频最终进入同一个语言模型空间。

## 时空 Attention 分解

假设视频有 $F$ 帧，每帧有 $P$ 个 patch。直接对全部 $FP$ 个视觉 token 做全局 Attention，复杂度近似为：

$$
O((FP)^2)
$$

K3 将其分解为：

1. 帧内空间 Attention；
2. 帧间时间 Attention。

概念上变成：

$$
O(FP^2+PF^2)
$$

这样仍然能够建模：

- 每一帧内部的空间关系；
- 同一位置跨帧的变化关系；

但避免所有空间位置和所有帧之间做完全两两交互。

这不是简单的精度妥协，而是视频进入 1M-token 统一上下文的必要工程设计：

> **视频 token 随帧数和分辨率同时增长，不能把全部时空 token 直接送进标准全局 Attention。**

## 时间维度压缩：Temporal Pooling

视频 token 数量的主要增长来源之一是帧数。时间 pooling 会：

- 合并相邻帧的一部分信息；
- 保留较慢变化的内容；
- 压缩冗余帧；
- 把 token 预算留给关键空间细节和语言推理。

代价是时间分辨率下降：

- 极短动作可能丢失；
- 快速变化可能被平均；
- 精细时序定位能力可能受限。

因此 K3 的取舍是：

> **牺牲部分时间分辨率，换取视频进入 1M-token 统一上下文的能力。**

## 空间 token 压缩：2×2 Pixel Shuffle

技术报告称，2×2 `pixel shuffle` 将视觉 token 数量压缩四倍。

以 $3584\times3584$ 图像和 patch size 14 为例：

$$
\frac{3584}{14}=256
$$

初始 patch 数约为：

$$
256\times256=65,536
$$

2×2 下采样后约为：

$$
\frac{65,536}{4}=16,384
$$

这还没有计算：

- 文本上下文；
- 多张图片；
- 视频帧；
- Agent 的历史轨迹；
- 工具返回的截图；
- 中间生成结果。

因此 pixel shuffle 的主要目标不是增强视觉表达，而是控制视觉 token budget：

```text
高分辨率输入
    ↓
ViT 提取局部特征
    ↓
2×2 token 压缩
    ↓
送入 1M context 的语言主干
```

代价是空间细节被压缩。K3 用 OCR、坐标监督、高分辨率视觉数据和程序化视觉数据来补偿这种损失。

## 为什么加入绝对坐标和归一化坐标监督

K3 的视觉数据同时使用：

- absolute coordinates；
- normalized coordinates $[0,1]$。

### 8.1 绝对坐标

适合具体界面操作：

```text
点击 x=820, y=460
```

它直接对应当前屏幕的像素位置。

### 8.2 归一化坐标

归一化坐标为：

$$
\hat{x}=\frac{x}{W},\qquad
\hat{y}=\frac{y}{H}
$$

这样同一个目标在不同分辨率和缩放比例下仍保持一致的位置表示。

例如：

```text
绝对坐标：1200 px
归一化坐标：0.75
```

当图像从 1600px 缩放到 3200px 时，绝对坐标会变化，而归一化位置仍然稳定。

坐标监督与 pixel shuffle 是互补关系：

- pixel shuffle 降低视觉 token 数；
- 坐标监督强化空间定位能力。

这直接服务于：

- GUI 操作；
- 网页交互；
- 屏幕定位；
- 视觉工具调用；
- 不同分辨率下的泛化。

## 为什么加入 Web、SVG、3D、Game、CAD 数据

K3 的视觉目标不是传统的“识图”，而是：

> **视觉理解 + 代码生成 + 工具执行 + 视觉验证。**

| 数据 | 训练的能力 |
| --- | --- |
| Webpage 截图与代码 | 视觉—HTML/CSS 对应 |
| SVG | 图形结构与可编辑表示 |
| 3D asset | 空间结构、视角和几何 |
| Game | 状态、界面和动作反馈 |
| CAD | 工程图、结构和精确空间关系 |
| OCR | 细粒度文字读取 |
| 视频 | 时间变化和过程理解 |

代码与渲染视觉的配对形成了一个可验证闭环：

```text
HTML/CSS/SVG/代码
        ↓
浏览器或渲染器
        ↓
截图
        ↓
模型比较目标与结果
        ↓
修改代码
```

这正是视觉 Agent 和 Web development 能力所需要的训练形态。

## Native Vision 背后的变化链条

### 10.1 传统路线

```text
视觉模型先学通用视觉语义
        ↓
语言模型单独训练
        ↓
通过 projector/adapter 做模态对齐
        ↓
视觉能力接入语言模型
```

优点：

- 视觉编码器有成熟初始化；
- 训练早期可能更容易；
- 独立视觉任务的能力通常较稳。

缺点：

- 对比学习目标和语言生成目标不完全一致；
- 视觉表示空间需要被重新改造；
- 视觉、projector、LLM 之间存在接口冲突；
- 对 OCR、布局、视觉代码和 Agent 反馈不一定最优；
- 大规模联合训练中可能出现梯度尖峰。

### 10.2 K3 路线

```text
视觉与文本从第一步就联合出现
        ↓
视觉特征直接接受语言模型目标塑形
        ↓
图像、视频、文本共享同一上下文
        ↓
视觉成为生成、行动和验证的一部分
```

K3 用以下手段抵消成本：

```text
RMSNorm + 无 bias
        → 稳定视觉塔训练

空间/时间 Attention 分解
        → 控制视频计算

Temporal Pooling
        → 控制帧数增长

Pixel Shuffle
        → 控制空间 token 数

坐标监督 + 程序化数据
        → 补偿压缩后的细节与空间能力

Native NTP
        → 让视觉表示直接服务语言和 Agent 任务
```

## 这次变化的真正含义

K3 没有提出一种完全全新的 Vision Transformer。它更像是在已有视觉骨架上完成了三次重新设计：

1. **重新设计训练入口**：从 SigLIP 初始化转向从零联合训练；
2. **重新设计监督目标**：从对比语义对齐转向语言建模和 Agent 任务；
3. **重新设计系统路径**：空间—时间分解、时间池化、token 压缩，适配 1M context。

因此，Native Vision 的真正创新不是：

> “MoonViT-V2 在任何场景都比 SigLIP 更强。”

而是：

> **在足够大的多模态语言模型中，视觉编码器不必先被训练成一个独立的通用视觉模型；它可以直接围绕语言生成和 Agent 交互目标塑形。**

但这依赖于足够强的数据、训练算力和联合优化基础设施。在小规模模型或视觉数据不足的场景中，`SigLIP` 这类预训练初始化仍可能更划算。K3 的结果说明的是：**在 K3 自身的规模和数据配方下，从零联合训练已经足以匹配对比预训练初始化，并且优化更稳定。**

## 最终总结

> **K3 的 Native Vision 把视觉从“接入语言模型的外部模块”变成了“语言模型从第一天就共同学习的感知通道”：用从零联合训练解决表示目标错位，用 RMSNorm 和无 bias 稳住优化，用时空分解和 token 压缩解决长视频与 1M 上下文成本，再用 OCR、坐标、网页和视觉代码数据把视觉能力推向 Agent 闭环。**
