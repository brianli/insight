## 2. 模型架构：静态结构设计

回答「模型长什么样」—— 网络的静态结构，描述 tensor 流转路径、模块组合方式、参数组织。

| 模块 | 核心内容 |
|---|---|
| **Hybrid Attention** | 每 block: 3 层 KDA (线性循环注意力) + 1 层 Gated MLA (全局 softmax 注意力), 末端额外 1 层 MLA<br/>KDA 用 lower-bounded sigmoid decay ($g_{\min} = -5$) 约束 log-decay 范围，使全部 tiles 走 Tensor Core；Gated MLA 用 NoPE，无显式位置编码 |
| **Attention Residuals (AttnRes)** | 每层通过 learnable pseudo-query 选择性 attends embedding 和所有前序层输出<br/>实际使用 Block AttnRes：93 层分为 8 blocks，block 内求和压缩，跨 block 做 full softmax attention<br/>通信开销从 $O(Ld)$ 降至 $O(Nd)$ |
| **Stable LatentMoE** | 896 个 routed experts，每 token 激活 16 个，sparsity=56；2 个 shared experts/层<br/>SiTU-GLU ($\beta_1\tanh(x/\beta_1) \odot \sigma(x)$ with $\beta_1=4, \beta_2=25$) 抑制激活爆炸<br/>Quantile Balancing 用 router score 分布直接反推 expert bias，实现精准负载均衡 |
| **MoonViT-V2** | 27 层 ViT (~0.4B 参数)，从零用 next-token prediction 训练<br/>图像/视频参数共享，pixel-shuffle 2×2 下采样控制 token 数 |
| **Per-Head Muon** | Q/K/V 投影矩阵按 head 维度分别做 Newton-Schulz 正交化，避免 head 间 update scale 不均衡 |
| **MTP Layer** | 1 层多 token 预测模块，后 fine-tune 为 EAGLE-3 draft model 加速推理 |

**架构定义了模型的上限** — 注意力机制决定能看多长、MoE 决定能放多大、AttnRes 决定能叠多深。

## 3. 训练范式：动态过程设计

回答「模型怎么练出来」—— 从数据到权重的全过程策略，包括数据构造、训练阶段、优化目标、环境设计。

| 阶段 | 核心内容 |
|---|---|
| **预训练** | 四大文本域 (Web/Code/Math/Knowledge) + 视觉语料<br/>原生多模态 (语言和视觉从第一天联合优化)<br/>cosine decay 学习率 (WSD 和 cosine 各自独立搜索最优超参数后 cosine 胜出)<br/>四阶段上下文课程 8K→64K→256K→1M<br/>合成长上下文数据：打散排列多模态文档，迫使 answer 依赖分散在 1M 内的信息 |
| **SFT** | 上代 Kimi 模型合成 agentic 轨迹 + multi-stage 验证 + human-in-the-loop<br/>用 XTML chat template 序列化<br/>从 SFT 起即开启 MXFP4 QAT |
| **RL (3 域 × 3 effort)** | General / General Agents / Coding Agents<br/>每个域在 {low, high, max} 三个 effort level 训练，共 9 个专家<br/>算法: Partial Rollout (前 $\lambda$ 完成即触发优化) + Reasoning Effort Budget Control (超 budget 则 reward=-1) + Agentic GRM (read→rubric→score→record) |
| **MOPD 蒸馏** | 多教师在策略蒸馏<br/>reward = $\text{clip}(\log\frac{\pi_{\text{teacher}}}{\pi_{\text{student}}}, -R_{\max}, R_{\max})$<br/>将 9 个专家的能力合并为单一模型 |
| **环境/任务设计** | Unified White-Box RL (可配置组合多种 harness)<br/>Knowledge-Graph-Guided 任务合成<br/>AgentENV microVM 沙箱 (Pause/Resume/Fork/Snapshot)<br/>Personal Assistant (模拟 Gmail/Slack/Notion, 跨越虚拟数天)<br/>AET (验证器闭环, 无参考轨迹)<br/>Kernel Optimization (性能 roofline 评分)<br/>Web Dev (确定性测试 + 模型评判) |
| **推理部署训练** | MTP → EAGLE-3 draft model, 直接优化 acceptance rate 而非 KL<br/>MoE 权重 MXFP4, 激活 MXFP8, 从 SFT 贯穿 RL |

**训练范式决定了模型的实际效果下限** — 练了什么环境、见了多复杂的数据、RL 给什么 reward signal。

## 4. 架构与训练范式的区别

| | 架构 | 训练范式 |
|---|---|---|
| 性质 | 静态结构 | 动态过程 |
| 回答的问题 | 模型长什么样 | 权重怎么来 |
| 设计重点 | 信息流路径、参数组织 | 数据、reward、环境 |
| 变更成本 | 高 (需 retrain 或重新验证) | 中 (可复用同一架构) |
| 对性能的影响 | 决定了天花板 | 决定了能摸到多高 |

### 双向制约和协同进化 — 三个 K3 案例

**Case 1: KDA 定体量, 上下文课程定能力**
> KDA 的 $O(1)$ 状态使 1M 上下文在架构层面成为可能。但如果只在 8K 数据上训练, KDA 的 long-range 能力根本不会被激活。于是训练范式设计了合成长上下文数据和四阶段课程。**架构给出可能性, 训练范式压榨出全部潜力。**

**Case 2: MoE 爆炸触发 SiTU-GLU, 量化均衡让 RL 不崩**
> 896 experts 是架构参数选择。训练中激活值爆炸 (vanilla SwiGLU × 多层级联矩阵乘法) 和负载失衡是训练范式暴露的问题。SiTU-GLU 和 Quantile Balancing 是为此设计的架构组件。然后 MOPD 蒸馏期间，量化平衡让 9 个教师的训练都稳定跑通 — **架构反过来支撑了训练范式的可行性。**

**Case 3: MoonViT-V2 从零训练**
> 过去用 SigLIP 初始化是训练范式的选择。K3 改为从零训练，是训练稳定性驱动的决策 (SigLIP 初始化梯度尖峰频繁)。结果发现对比预训练对多模态 LLM **不是必需的** — 训练范式的改变反过来影响了架构理解。

## 5. 基础设施：四个关键交叉点

### 5.1 KDA 架构 ↔ KDA 系统协同设计

KDA 的 $S_t \in \mathbb{R}^{d_k \times d_v}$ 是**固定大小** — 这是架构属性的核心。带来了三个基础设施挑战：

| 架构特征 | 带来的挑战 | 基础设施方案 | 成本节省逻辑 |
|---|---|---|---|
| recurrent state 跨 chunk 串行传播 | GPU 偏好并行，串行部分 SMs 闲置 | **FlashKDA**: 重叠 intra-chunk 并行计算和 cross-chunk 串行 state 传播 | 训练吞吐不打折 |
| state 固定大小 (vs softmax KV cache 随序列增长) | softmax 的 CP 方法不适用 KDA | **KCP**: 各 rank 计算局部 $M_T$ 和 $\tilde{S}_T$，一次 all-gather 后 prefix scan 恢复入站 state。**通信量不随序列长度增长** | 长序列训练不被通信带宽卡死 |
| decoding 时 MTP 回滚需恢复 state | 全量 state 缓存太重 | 缓存**投影输入**而非 state (与 ReplaySSM 同类设计)，on-chip 重建 | decoding 延迟几乎不因 MTP 而增加 |

**逻辑**: 架构给了 $O(1)$ 状态的优势，基础设施负责把这个优势兑现为计算效率。

### 5.2 Stable LatentMoE ↔ MoonEP + Memory-Efficient Training

896 experts、16 active/token — 架构选择。极端稀疏放大两个工程问题：

| 问题 | 架构层面 | 基础设施层面 | 关系 |
|---|---|---|---|
| 负载不均 | **QB**: router score 分位数反推 bias | **MoonEP**: 每 rank 固定 $S \times K$ token，bounded redundant experts 保证完美负载均衡 | QB 让 routing 均衡，MoonEP 保证即使有残差也不影响硬件利用。两者协同才**消除了 per-layer host 同步** |
| 内存爆炸 | **SiTU-GLU**: 激活值有界 | **统一 activation manager**: FP8 + offload 按 tensor 粒度组合<br/>**SonicMoE 风格梯度改写**: 消除 backward 对 forward output 的依赖 | 架构控制数值范围 → 基础设施可更激进量化/offload → 内存够用 |
| 小 batch GEMM memory-bound | 16 experts/token 导致每个 expert token 数极少 | **WarpDecode 风格 kernel**: 每个 warp 负责一个 output neuron，流式读取权重 | 架构定义稀疏模式，kernel 按此模式设计内存访问 |

**逻辑**: 架构定义计算图和通信模式，基础设施把模式映射到硬件。K3 的特别之处在于 — 架构组件在设计时已考虑基础设施约束。

### 5.3 AttnRes ↔ 内存和通信优化

AttnRes 需要保留前序 layer 输出。Naive 做法是 $O(Ld)$ 内存 — 93 层 × 7168 维，PP 下直接炸裂。

| 架构选择 | 基础设施优化 | 协调方式 |
|---|---|---|
| **Block AttnRes**: 93 层分 8 blocks，block 内求和压缩 | **Cache-based pipeline comm**: 只增量传输新 block 表征 | 架构的 block 分组 → 通信从 $O(Ld)$ 降至 $O(Nd)$ → 适配 PP 调度 |
| Block 表征在多层间共享 | **统一 activation manager**: block 表征放 GPU 不 evict，其余按需 offload | 架构给复用机会 → 基础设施利用这个减少存取 |
| 推理时 block 表征反复读取 | **Sequence Parallelism**: 每个 token 只在一张卡上物化，TP all-reduce 分解为 reduce-scatter + all-gather | 架构的 block 结构适配 SP 切分 |

AttnRes 的 block 设计本身是**架构层面的 infrastructure-aware 设计** — $N \approx 8$ "recovers most of the benefit"，说明 block 分组对效果的影响可忽略，但对工程可行性是决定性的。

### 5.4 1M Agentic RL 训练范式 ↔ KV Cache + Sandbox

最典型的训练范式与基础设施互相定义案例：

| 训练范式需求 | 基础设施方案 | 为什么必须协同设计 |
|---|---|---|
| Partial Rollout: 前 $\lambda$ 完成即训练，未完成的 resume 下轮 | **External KV Cache Pool** write-back + **AgentENV** checkpoint/resume (133ms/49ms) | 若基础设施不支持 pause/resume，partial rollout 只能是理论方案。反之，若无 partial rollout 这种范式，KV cache write-back 就没有设计动机 |
| 1M 上下文 + multi-step rollout → KV cache 压力递增 | **Auto-throttling Scheduler**: 根据 runtime 信号动态调整并发 | 训练范式定义 trajectory 增长模式 → 调度器按此设计 throttle 策略 |
| MOPD 蒸馏需 reference model forward | **Gradient buffer reuse**: reference model 权重流式填入 policy model 的 gradient buffer slot | 训练范式要求多模型共存 → 基础设施用 buffer 复用代替额外 GPU 内存 |

**AgentENV 的四个原语** — 为 agentic RL 量身定制：

| 原语 | 对应训练步骤 | 优化效果 |
|---|---|---|
| Pause | 推理等待 (占沙箱生命 98%) | 释放全部 CPU/内存 |
| Resume | Partial rollout 进入下一轮 | 从精确断点恢复 |
| Fork | Reward judging | 不污染原始沙箱状态 |
| Snapshot | 超长 trajectory 恢复 | 增量 checkpoint (133ms) |

## 6. 三层双向依赖总结

```
模型架构 (KDA, MoE, AttnRes)
       │
       │ 定义 computational pattern 和 memory footprint
       │ 要求基础设施提供：并行策略、内存管理、通信模式
       ▼
基础设施 (MoonEP, FlashKDA, KCP, AgentENV, KDA prefix cache)
       │
       │ 提供可扩展的运行环境
       │ 使训练范式在 2.8T/1M 规模下可执行
       ▼
训练范式 (SFT → 3×3 RL → MOPD, AgentENV 中的多环境训练)
       │
       │ 暴露架构在训练中的问题 (激活爆炸、负载失衡)
       │ 驱动架构组件 (SiTU-GLU, QB) 的设计迭代
       ▼
模型架构  ←  (反馈循环)
```

### 关键不对称性

| 方向 | 性质 | K3 体现 |
|---|---|---|
| 架构 → 基础设施 | **硬约束** | KDA 决定必须有 KCP，MoE 决定必须有 MoonEP |
| 训练范式 → 基础设施 | **工作量定义** | Partial rollout 和多步 agentic task 决定 KV cache 管理和沙箱设计 |
| 基础设施 → 架构 | **软反馈** (infrastructure-aware architecture) | Lower-bounded decay 为 Tensor Core 全覆盖而设计<br/>Block AttnRes 为降低通信而设计 |

### 核心结论

如果只算架构和训练范式而忽略基础设施，K3 就只是"又一个 big MoE"。让它成为真正可用的 3T 级模型的，恰恰是这三层的联动。**Lower-bounded decay 是这一哲学的最佳注脚** — 把无界 Softplus 换成 $g_{\min} = -5$ sigmoid，表面上是微小的数学改动，实质是为了让 Tensor Core 全覆盖 diagonal tiles。这是算法和系统在设计层面就融为一体的产物，不是"算法设计好了再优化系统"。

## 7. 扩展：模型全生命周期七层体系

上述三层 (架构、训练范式、基础设施) 是模型的**核心技术栈**，但一个到达用户手中的大模型需要更多维度。以 K3 为实例展开完整七层：

```
        产品与用户体验 (Kimi Chat / Kimi Code / API)
                        ↑
              ┌── 部署与服务 ──┐
              ↑               ↑
         安全与对齐 ←──────→ 评估体系
              ↓               ↓
         ┌──────── 核心技术栈 ────────┐
         │   架构  ↔  训练范式  ↔  基础设施   │
         └────────────┬───────────────┘
                      ↑
                数据工程
                      ↑
              生态与迭代策略
```

## 8. 数据工程

技术报告 §3.1 论述了大量数据工程细节，这是一个独立且体量巨大的领域。

### 8.1 K3 具体做法

| 子项 | K3 具体做法 |
|---|---|
| **数据源设计** | 四大文本域: Web Text, Code, Mathematics, Knowledge；视觉语料: captions, interleaved image-text, OCR, perception, video, visual coding |
| **过滤与清洗** | Rule-based heuristics + classifier quality scoring + deduplication；长文本专用 pipeline: exact/fuzzy dedup + 帧级 perceptual hash for video + 结构验证 + heuristic + classifier-based quality filtering |
| **数据合成** | 知识/数学语料用 style-perspective-diverse prompting + chunk-wise autoregressive generation + fidelity verification against source documents；长上下文数据: 排列拼接多模态文档和子任务，迫使 answer 依赖分散在 1M 内的信息 |
| **数据配比** | 各 domain 采样率通过小模型 ablation 实验确定；长文本在 cooldown 阶段上采样 |
| **数据去污** | 防止 benchmark 数据泄露到训练集 |

### 8.2 与其他层的关系

| 与哪层的关系 | 具体体现 |
|---|---|
| 数据 → 架构 | 长文档需要 KDA 来高效编码；视觉数据推动 MoonViT-V2 从零训练 |
| 数据 → 训练范式 | 数据分布决定预训练权重分布；合成长上下文数据直接设计 training curriculum 的结构 |
| 数据 → 评估 | 去污确保 benchmark 分数反映真实能力 |

### 8.3 关键认知

模型上限受架构约束，但**模型的实际知识面由数据决定**。K3 的 knowledge-heavy benchmark 表现 (GPQA 93.5) 和 research-level 短板 (CritPt 23.4) 本质上反映了数据覆盖的广度和深度。**数据工程是整个体系的「地基」** — 没有高质量、高多样性的训练数据，再好的架构也只是空壳。

### 9.2 与其他层的关系

| 与哪层的关系 | 具体体现 |
|---|---|
| 评估 → 训练范式 | 内部 eval 频繁迭代以指引下一次训练的数据和算法方向。eval 发现的 failure modes 直接驱动数据收集和 RL reward 设计 |
| 评估 → 安全 | 网络安全专项 (Tier 1 & 2) 评估模型在真实攻击场景中的能力边界，为安全决策提供依据 |
| 评估 → 架构 | 如果 eval 反复暴露某些问题 (如 long-range reasoning weak)，可能推动架构调整 (如增强 AttnRes 的跨层信息流) |
| 评估 → 部署 | 成本效率评估直接指导推理部署的优化方向和产品定价 |

### 9.3 关键认知

评估不是「跑完 benchmark 就完了」— 内部 eval 频繁迭代以指引下一次训练的数据和算法方向。**评估体系是连接「当前模型表现」和「下次迭代目标」的反馈回路**。同时，K3 的评估体系展示了完整度：公开 40+、内部 20+、第三方多家独立验证、网络安全专项 — 这种组合提供了单靠任何一个维度都无法得到的完整画像。

## 10. 安全与对齐

公开报告中安全意识层面的细节相对有限，但几个关键信号值得关注。

### 10.1 K3 体现

| 子项 | 具体做法 |
|---|---|
| **网络安全** | 主动评估 Tier 1 (漏洞发现，覆盖 Linux kernel, databases, AI services, web frameworks, blockchain, VPN) 和 Tier 2 (漏洞利用，36 tasks)；接受第三方 (UK AISI/NIST CAISI) 独立评估 |
| **Reward Hacking 防御** | Kernel 任务 hacking 检测系统 (检测 CUDA graph replay, input caching, precision reduction 等策略，持续扩展新规则)；AET 中用 hidden verifier 评估 held-out 场景 + penalty-based rewards under limited submission budgets |
| **量化感知训练** | MXFP4/MXFP8 QAT 从 SFT 开始贯穿整个后训练，不是训练完再加的「后处理」 |
| **Agent Behavior 评估** | Agent Behavior Bench 不仅评结果正确性，还评 tool-use 行为、效率和纪律 — 这实际上是安全的对齐评估 |
| **沙箱隔离** | AgentENV microVM 基于 Firecracker 的强隔离，既是为了性能 (pause/resume)，也是为了安全 — 防止 agent 的恶意操作影响宿主机 |

### 10.2 未公开部分

多语言安全、有害内容过滤、refusal 训练策略、越狱防御 — 公开 tech report 中未涉及，但这不代表没有。

### 10.3 与其他层的关系

| 与哪层的关系 | 具体体现 |
|---|---|
| 安全 ↔ 训练范式 | Reward hacking 防御是 RL reward design 的一部分；安全评估暴露的问题会驱动 RL 的 reward 修正 |
| 安全 ↔ 基础设施 | AgentENV 的 microVM 隔离同时服务于性能 (pause/resume) 和安全 (sandbox isolation)；两者在设计层面耦合 |
| 安全 ↔ 评估 | 网络安全专项评估和安全对齐评估是评估体系的子集，但独立于 benchmark 指标 |
| 安全 → 产品 | 安全评估结果影响模型是否适合公开发布、是否需要 cyberguard / refusal 等保护措施 |

### 10.4 关键认知

**安全不是训练完再加的「过滤器」**，而是贯穿评估和训练的持续过程。AgentENV 中的 microVM 隔离既优化了训练效率，也防范了 agent 误操作 — **性能优化和安全防护在这个维度上不是 trade-off，而是协同**。Reward hacking 防御体系持续演进的事实也说明：安全是一个动态博弈，不是一个一次性工程。

## 11. 部署与服务

技术报告 §5.4 详细覆盖了推理引擎层，但一个面向数百万用户的产品服务还有更多层面。

### 11.1 推理引擎层

| 子项 | K3 具体做法 |
|---|---|
| **混合架构缓存** | KDA-aware prefix cache: 统一 KDA state 和 MLA KV cache 的 paged pool；前缀哈希细化为 512-token hash block (vs 物理 6144-token block)；双阶段 lookup (MLA 匹配 → KDA checkpoint 验证)；concurrent scheduling 下的三阶段一致性保证 |
| **推理 Kernel** | KDA decoding: 缓存投影输入而非 state (与 ReplaySSM 同类设计), on-chip 重建 + 单 kernel 融合；Block AttnRes: inter-block 在 side stream 执行, intra-block 融合进 TP all-reduce；Stable LatentMoE: latent projection 与 MoE router 融合 GEMM, WarpDecode token-centric kernel |
| **量化部署** | MoE expert 权重 MXFP4, 激活 MXFP8；非 MoE 模块 (attention, latent MoE projections, shared experts, routers) 保持高精度 |
| **投机解码** | MTP layer → EAGLE-3 draft model, 训练阶段直接优化 $L_{\text{LK}}$ (acceptance rate) 而非 KL-divergence |

### 11.2 调度系统层

| 子项 | K3 具体做法 |
|---|---|
| **Service Discovery** | Cache-aware affinity scheduling: consistent hashing 将每 session 绑定到两个集群 (primary + hot standby)，保持 cache locality 同时限制故障影响范围 |
| **Admission Control** | Budget-based admission control: 为短请求和长请求分配独立资源预算，防止 bursty 长上下文流量挤占短请求 |


### 11.3 产品层

| 子项 | K3 具体做法 |
|---|---|
| **Kimi Chat** | 面向普通用户的多模态对话产品 |
| **Kimi Code** | 面向开发者的 coding agent CLI 工具 |
| **开发者 API** | 面向企业和开发者的 API 服务 |

### 11.4 与其他层的关系

| 与哪层的关系 | 具体体现 |
|---|---|
| 部署 ↔ 架构 | KDA prefix cache 的物理块大小 (6144 tokens) 和 hash block (512 tokens) 的分离是由 KDA checkpoint 的稀疏性和 MLA 的细粒度共同决定的 — 架构特征直接定义了缓存的可能形状 |
| 部署 ↔ 训练范式 | 投机解码的 draft model 是从训练的 MTP layer fine-tune 而来；MXFP4 量化在 SFT 阶段就开始适应 |
| 部署 ↔ 评估 | 成本效率评估 (score vs $/task) 直接量化部署优化的效果 |
| 部署 → 产品 | TTFT, 吞吐, 长上下文响应延迟, 多模态输入延迟 — 这些是用户体验的核心指标，由部署层决定 |

### 11.5 关键认知

部署层的优化直接决定用户体验和商业可行性。K3 的推理成本比 Fable 5 低 1/3~1/10 — 这个优势虽在评估中通过 benchmark 体现，但**源头在部署层的每一项优化**。Deployment-aware post-training (§4.1.4) — 从 SFT 起就量化训练、draft model 直接优化 acceptance rate — 意味着部署不是训练后的适配，而是从训练开始就参与的决策。

## 14. 全体系总结

三层核心技术栈 (架构、训练范式、基础设施) 定义了模型的**能力边界**，五层外围体系决定了模型的**可用性**：

| 层 | 回答的核心问题 | K3 最亮眼的东西 |
|---|---|---|
| 数据工程 | 喂了什么知识 | 全领域覆盖 + 合成长上下文 |
| 模型架构 | 理论上限在哪 | KDA + AttnRes + Stable LatentMoE 三合一 |
| 训练范式 | 怎么练出这些能力 | 3×3 RL + MOPD 蒸馏 + AgentENV 环境 |
| 基础设施 | 能不能规模化跑起来 | MoonEP 完美负载均衡 + KCP + 1M RL co-located |
| 评估体系 | 到底有多强 | 40+ 公开 + 20+ 内部 + 4 家第三方 |
| 安全与对齐 | 能不能安全放出去 | 自主发现 16 个 Zero-Day + 第三方审计 |
| 部署与服务 | 用户能用得起吗 | 成本低 1/3~1/10 + EAGLE-3 加速 + cache-aware 调度 |
| 生态与迭代 | 能持续多久 | 权重+论文+代码全开 + 季度发布节奏 |

**最常被低估的是数据工程和评估体系** — 前者决定知识面和能力边界，后者是整个开发循环的「方向盘」。而**安全和部署则决定一个模型是论文里的数字还是用户手里真正可用的产品**。

K3 之所以特别，不是因为在某一层做得极强，而是因为**七层同步推进到前沿** — 这在开源模型中前所未有。
