## 2. 模型架构：静态结构设计

回答「模型长什么样」—— 网络的静态结构，描述 tensor 流转路径、模块组合方式、参数组织。

| 模块 | 核心内容 |
|---|---|
| **Hybrid Attention** | 每 block: 3 层 KDA (线性循环注意力) + 1 层 Gated MLA (全局 softmax 注意力), 末端额外 1 层 MLA<br/>KDA 用 lower-bounded sigmoid decay ($g_{\min} = -5$) 约束 log-decay 范围，使全部 tiles 走 Tensor Core；Gated MLA 用 NoPE，无显式位置编码 |
| **Attention Residuals (AttnRes)** | 每层通过 learnable pseudo-query 选择性 attends embedding 和所有前序层输出<br/>实际使用 Block AttnRes：93 层分为 8 blocks，block 内求和压缩，跨 block 做 full softmax attention<br/>通信开销从 $O(Ld)$ 降至 $O(Nd)$ |
| **Stable LatentMoE** | 896 个 routed experts，每 token 激活 16 个，sparsity=56；2 个 shared experts/层<br/>SiTU-GLU ($\beta_1\tanh(x/\beta_1) \odot \sigma(x)$ with $\beta_1=4, \beta_2=25$) 抑制激活爆炸<br/>Quantile Balancing 用 router score 分布直接反推 expert bias，实现精准负载均衡 |
| **MoonViT-V2** | 27 层 ViT (~0.4B 参数)，从零用 next-token prediction 训练<br/>图像/视频参数共享，pixel-shuffle 2×2 下采样控制 token 数 |
| **Per-Head Muon** | Q/K/V 投影矩阵按 head 维度分别做 Newton-Schulz 正交化，避免 head 间 update scale 不均衡 |
| **MTP Layer** | 1 层多 token 预测模块，后 fine-tune 为 EAGLE-3 draft model 加速推理 |

**架构定义了模型的上限** — 注意力机制决定能看多长、MoE 决定能放多大、AttnRes 决定能叠多深。

## 3. 训练范式：动态过程设计

回答「模型怎么练出来」—— 从数据到权重的全过程策略，包括数据构造、训练阶段、优化目标、环境设计。

| 阶段 | 核心内容 |
|---|---|
| **预训练** | 四大文本域 (Web/Code/Math/Knowledge) + 视觉语料<br/>原生多模态 (语言和视觉从第一天联合优化)<br/>cosine decay 学习率 (WSD 和 cosine 各自独立搜索最优超参数后 cosine 胜出)<br/>四阶段上下文课程 8K→64K→256K→1M<br/>合成长上下文数据：打散排列多模态文档，迫使 answer 依赖分散在 1M 内的信息 |
| **SFT** | 上代 Kimi 模型合成 agentic 轨迹 + multi-stage 验证 + human-in-the-loop<br/>用 XTML chat template 序列化<br/>从 SFT 起即开启 MXFP4 QAT |
| **RL (3 域 × 3 effort)** | General / General Agents / Coding Agents<br/>每个域在 {low, high, max} 三个 effort level 训练，共 9 个专家<br/>算法: Partial Rollout (前 $\lambda$ 完成即触发优化) + Reasoning Effort Budget Control (超 budget 则 reward=-1) + Agentic GRM (read→rubric→score→record) |
| **MOPD 蒸馏** | 多教师在策略蒸馏<br/>reward = $\text{clip}(\log\frac{\pi_{\text{teacher}}}{\pi_{\text{student}}}, -R_{\max}, R_{\max})$<br/>将 9 个专家的能力合并为单一模型 |
| **环境/任务设计** | Unified White-Box RL (可配置组合多种 harness)<br/>Knowledge-Graph-Guided 任务合成<br/>AgentENV microVM 沙箱 (Pause/Resume/Fork/Snapshot)<br/>Personal Assistant (模拟 Gmail/Slack/Notion, 跨越虚拟数天)<br/>AET (验证器闭环, 无参考轨迹)<br/>Kernel Optimization (性能 roofline 评分)<br/>Web Dev (确定性测试 + 模型评判) |
| **推理部署训练** | MTP → EAGLE-3 draft model, 直接优化 acceptance rate 而非 KL<br/>MoE 权重 MXFP4, 激活 MXFP8, 从 SFT 贯穿 RL |

**训练范式决定了模型的实际效果下限** — 练了什么环境、见了多复杂的数据、RL 给什么 reward signal。

## 4. 架构与训练范式的区别

| | 架构 | 训练范式 |
|---|---|---|
| 性质 | 静态结构 | 动态过程 |
| 回答的问题 | 模型长什么样 | 权重怎么来 |
| 设计重点 | 信息流路径、参数组织 | 数据、reward、环境 |
| 变更成本 | 高 (需 retrain 或重新验证) | 中 (可复用同一架构) |
| 对性能的影响 | 决定了天花板 | 决定了能摸到多高 |

### 双向制约和协同进化 — 三个 K3 案例

**Case 1: KDA 定体量, 上下文课程定能力**
> KDA 的 $O(1)$ 状态使 1M 上下文在架构层面成为可能。但如果只在 8K 数据上训练, KDA 的 long-range 能力根本不会被激活。于是训练范式设计了合成长上下文数据和四阶段课程。**架构给出可能性, 训练范式压榨出全部潜力。**

**Case 2: MoE 爆炸触发 SiTU-GLU, 量化均衡让 RL 不崩**
> 896 experts 是架构参数选择。训练中激活值爆炸 (vanilla SwiGLU × 多层级联矩阵乘法) 和负载失衡是训练范式暴露的问题。SiTU-GLU 和 Quantile Balancing 是为此设计的架构组件。然后 MOPD 蒸馏期间，量化平衡让 9 个教师的训练都稳定跑通 — **架构反过来支撑了训练范式的可行性。**

**Case 3: MoonViT-V2 从零训练**
> 过去用 SigLIP 初始化是训练范式的选择。K3 改为从零训练，是训练稳定性驱动的决策 (SigLIP 初始化梯度尖峰频繁)。结果发现对比预训练对多模态 LLM **不是必需的** — 训练范式的改变反过来影响了架构理解。

## 5. 基础设施：四个关键交叉点

### 5.1 KDA 架构 ↔ KDA 系统协同设计

KDA 的 $S_t \in \mathbb{R}^{d_k \times d_v}$ 是**固定大小** — 这是架构属性的核心。带来了三个基础设施挑战：

| 架构特征 | 带来的挑战 | 基础设施方案 | 成本节省逻辑 |
|---|---|---|---|
| recurrent state 跨 chunk 串行传播 | GPU 偏好并行，串行部分 SMs 闲置 | **FlashKDA**: 重叠 intra-chunk 并行计算和 cross-chunk 串行 state 传播 | 训练吞吐不打折 |
| state 固定大小 (vs softmax KV cache 随序列增长) | softmax 的 CP 方法不适用 KDA | **KCP**: 各 rank 计算局部 $M_T$ 和 $\tilde{S}_T$，一次 all-gather 后 prefix scan 恢复入站 state。**通信量不随序列长度增长** | 长序列训练不被通信带宽卡死 |
| decoding 时 MTP 回滚需恢复 state | 全量 state 缓存太重 | 缓存**投影输入**而非 state (与 ReplaySSM 同类设计)，on-chip 重建 | decoding 延迟几乎不因 MTP 而增加 |

**逻辑**: 架构给了 $O(1)$ 状态的优势，基础设施负责把这个优势兑现为计算效率。

### 5.2 Stable LatentMoE ↔ MoonEP + Memory-Efficient Training

896 experts、16 active/token — 架构选择。极端稀疏放大两个工程问题：

| 问题 | 架构层面 | 基础设施层面 | 关系 |
|---|---|---|---|
| 负载不均 | **QB**: router score 分位数反推 bias | **MoonEP**: 每 rank 固定 $S \times K$ token，bounded redundant experts 保证完美负载均衡 | QB 让 routing 均衡，MoonEP 保证即使有残差也不影响硬件利用。两者协同才**消除了 per-layer host 同步** |
| 内存爆炸 | **SiTU-GLU**: 激活值有界 | **统一 activation manager**: FP8 + offload 按 tensor 粒度组合<br/>**SonicMoE 风格梯度改写**: 消除 backward 对 forward output 的依赖 | 架构控制数值范围 → 基础设施可更激进量化/offload → 内存够用 |
| 小 batch GEMM memory-bound | 16 experts/token 导致每个 expert token 数极少 | **WarpDecode 风格 kernel**: 每个 warp 负责一个 output neuron，流式读取权重 | 架构定义稀疏模式，kernel 按此模式设计内存访问 |

**逻辑**: 架构定义计算图和通信模式，基础设施把模式映射到硬件。K3 的特别之处在于 — 架构组件在设计时已考虑基础设施约束。

### 5.3 AttnRes ↔ 内存和通信优化

AttnRes 需要保留前序 layer 输出。Naive 做法是 $O(Ld)$ 内存 — 93 层 × 7168 维，PP 下直接炸裂。

| 架构选择 | 基础设施优化 | 协调方式 |
|---|---|---|
| **Block AttnRes**: 93 层分 8 blocks，block 内求和压缩 | **Cache-based pipeline comm**: 只增量传输新 block 表征 | 架构的 block 分组 → 通信从 $O(Ld)$ 降至 $O(Nd)$ → 适配 PP 调度 |
| Block 表征在多层间共享 | **统一 activation manager**: block 表征放 GPU 不 evict，其余按需 offload | 架构给复用机会 → 基础设施利用这个减少存取 |
| 推理时 block 表征反复读取 | **Sequence Parallelism**: 每个 token 只在一张卡上物化，TP all-reduce 分解为 reduce-scatter + all-gather | 架构的 block 结构适配 SP 切分 |

AttnRes 的 block 设计本身是**架构层面的 infrastructure-aware 设计** — $N \approx 8$ "recovers most of the benefit"，说明 block 分组对效果的影响可忽略，但对工程可行性是决定性的。

### 5.4 1M Agentic RL 训练范式 ↔ KV Cache + Sandbox

最典型的训练范式与基础设施互相定义案例：

| 训练范式需求 | 基础设施方案 | 为什么必须协同设计 |
|---|---|---|
| Partial Rollout: 前 $\lambda$ 完成即训练，未完成的 resume 下轮 | **External KV Cache Pool** write-back + **AgentENV** checkpoint/resume (133ms/49ms) | 若基础设施不支持 pause/resume，partial rollout 只能是理论方案。反之，若无 partial rollout 这种范式，KV cache write-back 就没有设计动机 |
| 1M 上下文 + multi-step rollout → KV cache 压力递增 | **Auto-throttling Scheduler**: 根据 runtime 信号动态调整并发 | 训练范式定义 trajectory 增长模式 → 调度器按此设计 throttle 策略 |
| MOPD 蒸馏需 reference model forward | **Gradient buffer reuse**: reference model 权重流式填入 policy model 的 gradient buffer slot | 训练范式要求多模型共存 → 基础设施用 buffer 复用代替额外 GPU 内存 |

**AgentENV 的四个原语** — 为 agentic RL 量身定制：

| 原语 | 对应训练步骤 | 优化效果 |
|---|---|---|
| Pause | 推理等待 (占沙箱生命 98%) | 释放全部 CPU/内存 |
| Resume | Partial rollout 进入下一轮 | 从精确断点恢复 |
| Fork | Reward judging | 不污染原始沙箱状态 |
| Snapshot | 超长 trajectory 恢复 | 增量 checkpoint (133ms) |

## 5.5 §5 Infra 部分的完整逻辑线

前面的三层关系回答“架构、训练范式、基础设施如何互相制约”。如果只看技术报告 §5 本身，它还存在一条更具体的**生命周期主线**：

```text
架构带来的新计算模式
        ↓
单卡 kernel 与跨卡并行
        ↓
3T 级预训练
        ↓
1M token Agentic RL
        ↓
在线推理与集群 SLO
```

因此 §5 的四个小节分别回答：

| 报告小节 | 核心问题 | 代表机制 |
|---|---|---|
| **§5.1** | KDA 的递归 state 如何适配 GPU 和 Context Parallelism？ | `FlashKDA`、`KCP` |
| **§5.2** | 3T MoE、多模态和超大激活如何训练？ | `MoonEP`、Unified Activation Manager、Dynamic CP |
| **§5.3** | 1M 长轨迹如何在模型侧与环境侧暂停、恢复和复用状态？ | External KV Cache Pool、Partial Rollout、`AgentENV` |
| **§5.4** | 混合 Cache、长短请求和集群故障如何被服务系统吸收？ | KDA-aware Prefix Cache、Affinity Scheduling、Admission Control |

更抽象地说：

```text
架构定义计算模式
    ↓
Kernel 适配单卡执行
    ↓
Parallelism 适配多卡执行
    ↓
Memory System 管理状态和显存
    ↓
Scheduler 管理动态负载
    ↓
Serving System 管理用户级 SLO
```

### 5.5.1 KDA：固定状态不是免费午餐

KDA 用固定大小的 recurrent state 替代随序列增长的 KV Cache：

$$
S_t=M_tS_{t-1}+\beta_t k_tv_t^\top
$$

它得到的是：

```text
固定大小 state，适合长上下文
```

同时失去的是：

```text
token 之间完全独立的并行性
```

所以 KDA 的系统问题从“Attention 的二次复杂度”转为“递归状态的串行传播”。`FlashKDA` 与 `KCP` 是两个不同尺度的回答：

```text
FlashKDA：卡内，隐藏 chunk 之间的 state propagation
KCP：跨卡，把 segment transition 组织成 prefix scan
```

`FlashKDA` 将 chunk 内 token-parallel 计算与 head-parallel recurrence 重叠，避免：

```text
计算 Chunk 1 → 等待 state → 计算 Chunk 2 → 等待 state
```

`KCP` 则为每个 rank 计算：

1. 累计转移矩阵 $M_{T\leftarrow1}$；
2. 从零状态产生的局部 state $\tilde{S}_T$。

每段状态写成：

$$
S_{\mathrm{out}}
=
\tilde{S}_T+M_{T\leftarrow1}S_{\mathrm{in}}
$$

再通过固定大小的状态交换和 prefix scan 恢复全局递归。因此：

```text
Softmax Attention：
通信载荷随序列长度增长

KDA + KCP：
同步固定大小的 recurrent state 片段
```

但不要把 KDA 误解成“天然容易并行”。KDA 只是压缩了历史状态；`KCP` 才是把递归 state 组织成跨卡并行算法。

KDA decode 还要面对 speculative decoding 的 rollback。K3 不为每个 draft position 保存完整 state，而是缓存 projected inputs，在 on-chip 重放 recurrence：

```text
少存储 ↔ 多重算
```

### 5.5.2 3T 预训练：三个瓶颈、三组方案

3T 级原生多模态 MoE 训练的三个核心瓶颈是：

```text
MoE token routing 不均衡
激活、梯度和优化器状态放不下
视觉编码器动态计算拖慢 pipeline
```

对应关系：

| 瓶颈 | 方案 | 本质 |
|---|---|---|
| EP 负载不均衡 | `MoonEP` | 把动态稀疏规整成固定硬件负载 |
| 显存不足 | Activation Manager、FP8、Recompute、Offload、P2P Muon | 把显存变成可组合的分层存储 |
| ViT 进入关键路径 | Dynamic CP、Pipeline Bubble Hiding | 把视觉计算隐藏在并行和 pipeline 空隙中 |

#### MoonEP：把动态稀疏规整成固定 shape

目标是让每个 EP rank 接收固定数量的 token：

$$
S\times K
$$

其中 $S$ 为 sequence length，$K$ 为每 token 激活的 expert 数。

`MoonEP` 的机制不是单一的“负载均衡”：

- 根据当前 routing 结果动态规划并预取冗余 expert；
- 用有界冗余保证始终存在可行平衡方案，报告给出的每 rank 上界约为 $E/R$；
- 预先计算 token 目的位置，做 zero-copy dispatch；
- 固定总 token 数，使 shape 静态可知，消除逐层 Host 同步；
- 根据 rank 内 expert token 分布做 workload-aware GEMM scheduling；
- 将 shared expert GEMM 放到独立 stream，与其他计算重叠。

核心判断：

> **MoE 的系统难点不是稀疏，而是动态、不规则和不均衡；MoonEP 把动态稀疏重新变成硬件喜欢的固定形状。**

#### Memory-efficient Training：把显存管理抽象成策略

K3 的 Unified Activation Manager 将每个 backward 所需 tensor 的存储方式抽象出来：

```text
保存 / Recomputation / Quantization /
GPU Offload / Remote Offload / 组合使用
```

典型组合包括：

- block-wise FP8 activation quantization + offload；
- element-wise operator recomputation；
- activation 按 layer 粒度预取，并与计算重叠；
- 主计算 stream 统一管理 GPU memory pool，降低碎片；
- MoE backward 通过数学改写移除对 forward output 的依赖；
- group GEMM backward 重算 dispatch，以计算换存储；
- AttnRes 共享 block representation，并用 checkpointing 降低保存量；
- 将 PP rank 间不均衡 activation remote offload；
- 使用 Pipeline ZeRO-2 gradient sharding and offloading；
- 用 P2P Muon 解决 ZeRO 参数分片与 Newton–Schulz 完整矩阵之间的冲突。

关键不是“用了 FP8”，而是：

> **显存管理从模型代码中解耦，成为可按 tensor 组合的存储系统。**

#### Multimodal Encoder Optimization：隐藏 ViT 的动态成本

大图和长视频会让视觉 encoder 成为 pipeline 的尾部瓶颈：

```text
文本计算完成
    ↓
等待某个大图 / 长视频 ViT
    ↓
整个 pipeline 被拖慢
```

K3 用 Dynamic CP 沿 patch 维度切分大图，并将 CP group 划分为多个 sub-CP groups，降低样本间负载不均衡；同时将 ViT forward/backward 拆分，把大部分计算塞进 PP bubble。

这里的系统原则是：

> **减少模块自身耗时，不等于减少端到端 step 耗时；能被已有并行空隙覆盖的计算，优先做 latency hiding。**

### 5.5.3 1M Agentic RL：基础设施从 tensor 管理转向状态机管理

§5.3 处理的不只是 tensor，还包括：

```text
模型推理 + 长轨迹状态 + KV Cache
+ 训练迭代 + 外部环境 + 沙箱生命周期
```

因此要同时管理：

```text
模型侧的长上下文状态
环境侧的 sandbox 世界状态
```

`Partial Rollout` 将长轨迹拆到多轮：

```text
第 i 轮：完成的轨迹先更新策略，未完成的轨迹暂停
第 i+1 轮：恢复未完成轨迹并继续执行
```

这要求：

```text
轨迹暂停
→ KV Cache 持久化
→ sandbox checkpoint
→ 下一轮恢复
→ 继续 rollout
```

#### External KV Cache Pool

K3 采用 write-back：

```text
活跃 decode：KV Cache 留在 GPU
idle prefix：被驱逐时写回 CPU DRAM
再次复用：预取回 GPU
```

KDA recurrent state 必须与 MLA KV blocks 一起 offload、prefetch 和恢复，因为二者共同构成一个 prefix 的完整状态。

#### Rollout Auto-throttling

轨迹越推进，context 越长，KV Cache 压力越大。固定并发数会在两端失效：

- 按最终长度设置：前期过于保守；
- 按早期长度设置：后期触发 cache pressure、preemption。

因此调度器根据 active request count、queued request count、KV Cache utilization 动态调节并发：

```text
早期提高并发，填满硬件
后期降低并发，避免过载
```

#### AgentENV

普通 container 不足以承载高探索性的 Agent，因为 Agent 可能运行容器、启动虚拟机，甚至造成 kernel panic、deadlock 或 reward hacking。`AgentENV` 使用 Firecracker microVM，在隔离性与环境真实性之间取得平衡。

四个原语对应四类训练需求：

| 原语 | 训练需求 | 作用 |
|---|---|---|
| `Pause` | 等待模型或工具返回 | 释放 CPU / memory |
| `Resume` | 下一轮继续未完成轨迹 | 从精确断点恢复 |
| `Fork` | 无副作用 reward judging | 复制同一世界状态 |
| `Snapshot` | 长任务容错与回滚 | 增量 checkpoint |

底层只保存自上次 checkpoint 后被修改的 memory pages；报告给出的最低 checkpoint latency 约 133 ms，resume latency 约 49 ms。训练与评估期间共创建了 51,219,741 个 sandboxes，涉及 1,505,678 个 images。

三者关系：

```text
Partial Rollout：
暂停策略轨迹

AgentENV：
暂停环境状态

External KV Pool：
暂停模型上下文状态
```

它们共同构成可执行的长程 Agent RL。

### 5.5.4 Online Serving：从单请求效率走向系统可预测性

在线服务要同时面对：

```text
混合 KDA / MLA cache
+ 新架构 kernel
+ 稀疏专家
+ 1M context
+ 长短请求成本相差三个数量级
+ 多租户 SLO
```

#### KDA-aware Prefix Cache

KDA state 是固定大小 recurrent state，Gated MLA KV 是随 token 增长的 KV block。一个 prefix 只有在两者都恢复时才可复用，因此 K3 将二者放入统一 paged pool，共享 allocation、reference counting、eviction 和 transfer。

K3 将物理存储粒度与逻辑索引粒度解耦：

```text
physical allocation block：粗粒度，例如 6144 tokens
prefix hash block：细粒度，例如 512 tokens
```

KDA checkpoint 只在 hash boundary 保存，因此可以在 6144-token physical block 内部命中 2560-token 边界：

```text
恢复 2560 token 位置的 KDA checkpoint
复用 MLA 前 2560 token 的 KV
从 token 2560 继续 prefill
```

这是一个通用原则：

> **物理存储粒度服务于分配效率，逻辑索引粒度服务于复用效率，两者不应强行绑定。**

#### High-performance Kernels

- KDA decode 缓存 projected inputs，在 fused kernel 中重放 recurrence，避免保存每个 draft position 的完整 state；
- Block AttnRes prefill 使用 sequence parallelism，decode 将 inter-block kernel 放入 side stream，并融合 intra-block merge、partial-sum update 和 RMSNorm；
- Stable LatentMoE 融合 latent down-projection 与 router，shard latent weights，将 output all-gather 融入 GEMM epilogue；小 batch decode 使用 token-centric、memory-bound 友好的 WarpDecode 风格 kernel。

#### Fleet-level Scheduling

1M context 下，一个请求可能有 400K prefix、只新增 4K tokens，cache hit 与 miss 的成本相差几个数量级。`Cache-aware affinity scheduling` 将请求路由到持有其 prefix cache 的 cluster，并用 consistent hashing 配置 primary / secondary cluster：

```text
Primary：常态服务并持有 cache
Secondary：故障接管，但需要重新 prefill
```

`Budget-based admission control` 则为不同 request class 分配独立资源预算，避免长请求突发污染短请求的 TTFT 和系统级 SLO。

## 5.6 把 §5 压缩成五个系统问题

| 系统问题 | K3 对应机制 | 核心判断 |
|---|---|---|
| 计算能否并行？ | `FlashKDA`、`KCP`、Dynamic CP、Pipeline Bubble Hiding | 把串行部分隐藏、分解或放进已有空隙 |
| 每张卡负载是否均衡？ | `MoonEP`、Workload-aware GEMM、Sub-CP、Activation Balancing | 分布式速度由最慢设备决定，尾部负载比平均负载重要 |
| 状态应该放在哪里？ | Activation Manager、FP8、Recompute、Offload、External KV Pool | 根据活跃度、恢复成本和带宽选择存储层级 |
| 状态能否暂停、恢复、复制？ | Partial Rollout、AgentENV、Checkpoint、Projection Replay | 长程 Agent 系统的基本抽象是可持久化状态机 |
| 动态流量下是否可预测？ | Auto-throttling、Affinity、Admission Control | 生产系统不只追求峰值吞吐，更要控制 SLO 尾部风险 |

## 5.7 第 4 部分与第 5 部分的关系

第 4 部分定义 workload，第 5 部分承载 workload：

| 第 4 部分提出的需求 | 第 5 部分提供的 Infra |
|---|---|
| 1M 长轨迹 | External KV Cache Pool |
| Partial Rollout | AgentENV Resume + KV state persistence |
| 多步工具调用 | Auto-throttling Scheduler |
| Agent 环境探索 | microVM Sandbox |
| 多模型 MOPD | Gradient-buffer Reuse |
| KDA 长上下文 | FlashKDA + KCP |
| 3T MoE 训练 | MoonEP + Memory-efficient Training |
| 部署成本约束 | Prefix Cache + Scheduling + Admission Control |

因此：

```text
第4部分：定义模型要学什么、如何获得 reward
第5部分：提供让这些训练过程可执行、可恢复、可扩展的系统
```

> **第 4 部分定义 workload，第 5 部分优化 workload 的执行成本。**

## 5.8 三个最重要的判断

### 判断一：K3 Infra 不是训练完成后的“优化层”

错误理解是：

```text
先设计架构
→ 训练模型
→ 最后用 Infra 优化速度
```

K3 更接近：

```text
架构、训练范式、Infra 同时设计
```

例如：

- KDA 的固定 state 影响 `KCP`；
- 896 experts 逼出 `MoonEP`；
- Partial Rollout 逼出 checkpoint/resume；
- KDA + MLA 逼出联合 prefix cache；
- AttnRes 的 block 化降低通信和存储成本。

### 判断二：K3 反复把不规则性转换成规则性

```text
递归 state
→ chunkwise / prefix scan

动态 expert routing
→ 固定 token shape

动态 activation
→ tensor-level storage policy

超长 trajectory
→ 可暂停、可恢复状态

混合 cache
→ 统一 paged pool

长短请求混部
→ 分级 resource budget
```

所以 §5 的底层主题是：

> **把模型天然的不规则性转换成硬件和集群能够处理的规则化工作负载。**

### 判断三：瓶颈从 FLOPs 扩展到状态管理

传统 LLM Infra 更常问：

```text
矩阵乘法够不够快？
```

K3 §5 更常问：

```text
状态在哪里？
什么时候搬？
能不能复用？
能否恢复？
谁在等待？
如何避免一个长任务拖死其他任务？
```

这正是从传统 LLM 训练 Infra 走向 Agent Infra 的分水岭。

## 6. 三层双向依赖总结

```
模型架构 (KDA, MoE, AttnRes)
       │
       │ 定义 computational pattern 和 memory footprint
       │ 要求基础设施提供：并行策略、内存管理、通信模式
       ▼
基础设施 (MoonEP, FlashKDA, KCP, AgentENV, KDA prefix cache)
       │
       │ 提供可扩展的运行环境
       │ 使训练范式在 2.8T/1M 规模下可执行
       ▼
训练范式 (SFT → 3×3 RL → MOPD, AgentENV 中的多环境训练)
       │
       │ 暴露架构在训练中的问题 (激活爆炸、负载失衡)
       │ 驱动架构组件 (SiTU-GLU, QB) 的设计迭代
       ▼
模型架构  ←  (反馈循环)
```

### 关键不对称性

| 方向 | 性质 | K3 体现 |
|---|---|---|
| 架构 → 基础设施 | **硬约束** | KDA 决定必须有 KCP，MoE 决定必须有 MoonEP |
| 训练范式 → 基础设施 | **工作量定义** | Partial rollout 和多步 agentic task 决定 KV cache 管理和沙箱设计 |
| 基础设施 → 架构 | **软反馈** (infrastructure-aware architecture) | Lower-bounded decay 为 Tensor Core 全覆盖而设计<br/>Block AttnRes 为降低通信而设计 |

### 核心结论

如果只算架构和训练范式而忽略基础设施，K3 就只是"又一个 big MoE"。让它成为真正可用的 3T 级模型的，恰恰是这三层的联动。**Lower-bounded decay 是这一哲学的最佳注脚** — 把无界 Softplus 换成 $g_{\min} = -5$ sigmoid，表面上是微小的数学改动，实质是为了让 Tensor Core 全覆盖 diagonal tiles。这是算法和系统在设计层面就融为一体的产物，不是"算法设计好了再优化系统"。

## 8. 数据工程

技术报告 §3.1 论述了大量数据工程细节，这是一个独立且体量巨大的领域。

### 8.1 K3 具体做法

| 子项 | K3 具体做法 |
|---|---|
| **数据源设计** | 四大文本域: Web Text, Code, Mathematics, Knowledge；视觉语料: captions, interleaved image-text, OCR, perception, video, visual coding |
| **过滤与清洗** | Rule-based heuristics + classifier quality scoring + deduplication；长文本专用 pipeline: exact/fuzzy dedup + 帧级 perceptual hash for video + 结构验证 + heuristic + classifier-based quality filtering |
| **数据合成** | 知识/数学语料用 style-perspective-diverse prompting + chunk-wise autoregressive generation + fidelity verification against source documents；长上下文数据: 排列拼接多模态文档和子任务，迫使 answer 依赖分散在 1M 内的信息 |
| **数据配比** | 各 domain 采样率通过小模型 ablation 实验确定；长文本在 cooldown 阶段上采样 |
| **数据去污** | 防止 benchmark 数据泄露到训练集 |

### 8.2 与其他层的关系

| 与哪层的关系 | 具体体现 |
|---|---|
| 数据 → 架构 | 长文档需要 KDA 来高效编码；视觉数据推动 MoonViT-V2 从零训练 |
| 数据 → 训练范式 | 数据分布决定预训练权重分布；合成长上下文数据直接设计 training curriculum 的结构 |
| 数据 → 评估 | 去污确保 benchmark 分数反映真实能力 |

### 8.3 关键认知

模型上限受架构约束，但**模型的实际知识面由数据决定**。K3 的 knowledge-heavy benchmark 表现 (GPQA 93.5) 和 research-level 短板 (CritPt 23.4) 本质上反映了数据覆盖的广度和深度。**数据工程是整个体系的「地基」** — 没有高质量、高多样性的训练数据，再好的架构也只是空壳。

## 9. 评估体系

技术报告 §6 不是简单展示 benchmark 分数，而是在建立一条完整的产品证据链：

```text
能力覆盖
    ↓
实验可比性
    ↓
真实工作流诊断
    ↓
安全边界
    ↓
第三方独立验证
    ↓
能力—成本可行性
```

它回答的不是一个问题，而是：

```text
模型有哪些能力？
比较是否公平？
真实工作流中是否可靠？
具体会在哪里失败？
高风险能力边界在哪里？
内部结论是否可信？
达到这些能力是否值得部署？
```

因此，§6 的核心不是“模型排名”，而是：

> **把模型能力转化为可比较、可诊断、可验证、可部署的证据。**

### 9.0 三类评估要分开

| 类型 | 主要问题 | 典型指标 |
|---|---|---|
| **能力评估** | 模型能不能完成任务？ | accuracy、pass rate、F1、Elo |
| **行为与边界评估** | 模型如何完成任务、哪里失败、风险边界在哪？ | tool-use quality、效率、纪律、漏洞发现/利用、failure modes |
| **经济评估** | 达到这个能力需要多少推理资源？ | score vs. cost per task |

三者不能互相替代：

```text
高分 ≠ 行为可靠
行为可靠 ≠ 安全
安全能力 ≠ 低成本
```

### 9.1.1 公开主评估：建立能力地图与横向位置

K3 将公开 benchmark 组织为四个能力轴：

| 能力轴 | 主要测量对象 | 代表问题 |
|---|---|---|
| **Reasoning & Knowledge** | 知识、推理和研究级问题 | 模型能否解决高难度抽象问题？ |
| **Coding** | 软件工程与长程代码执行 | 模型能否从需求理解走到可运行交付物？ |
| **Agentic** | 搜索、工具调用、企业工作流和电脑操作 | 模型能否在环境中持续行动并完成目标？ |
| **Vision** | 图像、视频、文档和视觉工具使用 | 模型能否把视觉输入接入推理和执行闭环？ |

这一步的逻辑是：

> **先定义能力空间，再在每个能力轴内部用多个 benchmark 采样，避免用一个总分掩盖能力结构。**

单个 benchmark 不能代表完整能力：

- `GPQA Diamond` 不能代表研究级开放问题；
- `ProgramBench` 不能替代长程软件工程；
- `BrowseComp` 不能代表电脑操作或企业协作；
- `OmniDocBench` 不能代表视频或视觉工具调用。

所以公开评估采用：

```text
能力轴
    ↓
多个任务分布
    ↓
多个指标
    ↓
能力画像，而不是单一分数
```

### 9.1.2 Baseline 与 Evaluation Configuration：先保证比较有效

K3 与 Claude Fable 5、GPT-5.6 Sol、Claude Opus 4.8、GPT-5.5 和 GLM-5.2 比较。目的不是证明所有任务第一，而是确认：

```text
哪些维度接近最强闭源模型？
哪些维度领先同档模型？
哪些维度仍存在明显差距？
```

benchmark 分数不是脱离实验协议的事实。必须明确：

```text
reasoning effort
temperature
top-p
harness
tool augmentation
任务版本
GPU / 硬件环境
运行次数
评判器与 leaderboard 版本
```

K3 的典型配置包括：

- 单步 reasoning / knowledge 使用 `top-p = 0.95`；
- coding 和 agentic 场景使用 `top-p = 1.0`；
- coding 任务可能使用 `Kimi Code`、`Claude Code` 或 `Codex` harness；
- 视觉 benchmark 区分是否使用 Python tool；
- vision 分数通常多次运行取平均；
- 某些任务固定版本、GPU 校准分支和官方 evaluation script。

因此：

> **Benchmark 分数只有在任务、harness、采样策略、工具、版本和统计方式透明时，才具有横向比较意义。**

要特别注意比较不对称：

- 不同模型可能使用不同 harness；
- 某些模型包含 fallback；
- 某些模型可能拒答或触发 cyberguard；
- 第三方 leaderboard 可能使用各自的配置；
- Elo 会随新增比赛动态漂移。

### 9.1.3 Public Results：看能力结构，不看单一总分

| 维度 | K3 主要结论 |
|---|---|
| Reasoning & Knowledge | `GPQA Diamond` 93.5%，接近 frontier；`HLE-Full`、`CritPt` 落后，research-level reasoning 是短板 |
| Coding | `ProgramBench` 77.8%、`SWE-Marathon` 42.0%，GPU kernel 和长程工程执行突出；不同 SWE 分布上并非全面第一 |
| Agentic | `BrowseComp`、`DeepSearchQA`、`MCPMark-Verified`、`AutomationBench` 等强；Elo 型 knowledge-work suite 仍落后 Claude Fable 5 |
| Vision | `OmniDocBench` 突出；Python tool 显著提升 `Math-Vision`、`ZeroBench-main`，体现模型能力与工具的互补 |

最终要读出的不是“K3 排第几”，而是：

```text
K3 在什么能力上强？
在什么能力上弱？
工具如何改变结果？
```

### 9.2 与其他层的关系

| 与哪层的关系 | 具体体现 |
|---|---|
| 评估 → 训练范式 | 内部 eval 频繁迭代以指引下一次训练的数据和算法方向。eval 发现的 failure modes 直接驱动数据收集和 RL reward 设计 |
| 评估 → 安全 | 网络安全专项 (Tier 1 & 2) 评估模型在真实攻击场景中的能力边界，为安全决策提供依据 |
| 评估 → 架构 | 如果 eval 反复暴露某些问题 (如 long-range reasoning weak)，可能推动架构调整 (如增强 AttnRes 的跨层信息流) |
| 评估 → 部署 | 成本效率评估直接指导推理部署的优化方向和产品定价 |

### 9.2.1 内部评估：把公开 benchmark 变成开发诊断系统

公开 benchmark 适合对外比较，但不适合快速指导下一轮训练，因为它们更新慢、覆盖有限、未必贴近产品流量，也很难解释失败轨迹。因此 K3 维护频繁刷新、贴近真实工作流的 internal evaluation suite。

它的作用不是再做一次排名，而是：

```text
发现 failure modes
        ↓
定位能力缺口
        ↓
修改数据、reward、harness 或训练策略
        ↓
重新评估
```

#### 三类内部任务

| 类别 | 主要测量内容 | 代表 benchmark |
|---|---|---|
| **Coding Capability & Experience** | 端到端软件工程、Web 开发、真实 coding workflow | Kimi Code Bench 2.0、Kimi Webdev Bench、Coding Experience |
| **General Agent Experience** | 多日任务、多 Agent 协作、自治执行、视觉 Agent、研究和专业工作 | 24/7 ClawBench 2.0、MIRA、KAET、Swarm Bench、Deep Research Bench、Finance Bench、Agent Behavior Bench |
| **Conversational Experience** | 事实性、幻觉、真实产品对话体验 | Faithfulness、Chat All-in-One Bench |

公开 benchmark 更像：

```text
模型是否做对一道题？
```

内部 benchmark 更接近：

```text
模型能否在真实工作流中持续、合适、可靠地工作？
```

#### 从结果正确扩展到过程质量

`Agent Behavior Bench` 不仅看任务是否完成，还看：

- tool-use behavior；
- efficiency；
- discipline；
- 是否陷入无效循环；
- 是否以合适方式完成任务。

Agent 评价函数由“结果正确”扩展为：

$$
\text{Agent Quality}
=
\text{Outcome}
+\text{Process}
+\text{Efficiency}
+\text{Discipline}
$$

这比单纯 pass rate 更接近真实产品价值。

#### 内部评估是训练反馈回路

```text
训练
  ↓
内部评估
  ↓
failure mode analysis
  ↓
数据 / reward / harness / 算法调整
  ↓
下一轮训练
```

所以评估体系不是开发末端的验收，而是训练系统的一部分。

### 9.2.2 网络安全评估：测量能力边界与滥用风险

网络安全是独立的风险分层评估轨道：

```text
Tier 1：漏洞发现 + PoC 复现
        ↓
Tier 2：端到端漏洞利用
```

Tier 1 要求模型在真实代码库中发现 genuine bugs、编写 proof of concept 并证明可复现，覆盖 Linux kernel、数据库、AI service、web framework、blockchain 和 VPN 等软件。

Tier 2 包括：

- user-space exploitation：16 tasks；
- Linux kernel exploitation：20 tasks。

每个任务都有可复现环境，并由人类专家确认可解，因此未完成任务可以作为与人类能力差距的证据。

安全能力不是一个标量：

```text
发现漏洞
    < 构造 PoC
    < 利用用户态漏洞
    < 绕过缓解措施
    < 完成内核级端到端利用
```

K3 在 Tier 1 和 user-space Tier 2 更强，但 hardened target 上的 exploit chain completion 仍是瓶颈。轨迹分析揭示四类失败：

1. 已取得 primitive，却无法完成 exploit chain 最后阶段；
2. 存在 mitigation 时策略选择不佳；
3. 陷入冗长、无效的 debugging loop；
4. 提交前没有充分验证最终 deliverable。

报告将结果定义为当前版本和当前覆盖范围下的 **lower bound**，不是能力上限。

### 9.2.3 第三方评估：降低自测偏差

| 第三方类型 | 评估方式 | 主要价值 |
|---|---|---|
| Artificial Analysis | 综合 Intelligence Index、行业 benchmark、成本数据 | 外部排名与成本视角 |
| Vals AI | GDP-weighted industry benchmark | 专业工作价值 |
| Arena | 人类偏好、Elo | 真实用户主观偏好 |
| UK AISI / NIST CAISI | 独立网络安全评估 | 校验高风险能力结论 |

正确区分：

```text
内部评估：高频、可诊断、服务训练迭代
第三方评估：独立、可对照、降低自我报告偏差
```

第三方结果的边界：

- 各家配置和 harness 可能不同；
- leaderboard 样本和排名会变化；
- Elo 会随新增比赛漂移；
- 不同机构的综合指数不可直接当作同一量纲。

正确读法是看多个独立来源是否共同支持大方向，不是机械比较所有数字。

### 9.2.4 成本效率：把能力分数转成产品价值

单看 benchmark score 隐含了错误假设：

```text
分数更高 = 模型更好
```

真实部署还要考虑每个任务的推理成本。K3 对 coding / agentic suites 同时比较：

```text
Score
vs.
Cost per task
```

理想模型应位于 Pareto frontier：

```text
不存在另一个模型：
分数更高且成本更低
```

K3 报告的核心结论：

- `Kimi Code Bench 2.0`：以约 38% 的 Claude Fable 5 成本取得仅低 4 分的成绩；
- high effort：接近 Claude Opus 4.8 max effort，成本约为其三分之一；
- `BrowseComp`：91.2%，每任务约 $2.03；
- `GDPval-AA v2` 与 `AA-Briefcase`：分数接近或位于前列，但成本显著更低。

成本效率是前面各章的综合结果：

```text
架构：KDA、MoE、AttnRes 降低计算与状态成本
训练：Deployment-aware post-training、QAT、EAGLE-3
基础设施：Kernel、Prefix Cache、Scheduling、Admission Control
最终：更低 cost per task
```

### 9.2.5 §6 的完整证据链

```text
公开 benchmark
   建立四大能力轴和跨模型相对位置
        ↓
配置与协议透明
   让比较具有可解释性
        ↓
内部 benchmark
   补齐公开任务未覆盖的真实工作流
        ↓
轨迹与 failure mode 分析
   从“多少分”推进到“为什么失败”
        ↓
网络安全专项
   测量高风险能力边界与滥用风险
        ↓
第三方独立验证
   降低内部自测偏差
        ↓
Score vs. Cost
   判断能力是否具有产品和经济可行性
```

| 问题 | §6 对应部分 |
|---|---|
| 模型覆盖哪些能力？ | Public Benchmarks |
| 横向比较是否公平？ | Baselines + Evaluation Configurations |
| 真实产品工作流表现如何？ | Internal Evaluation |
| 模型具体会在哪里失败？ | Failure-mode / Trajectory Analysis |
| 高风险能力边界在哪里？ | Cyber Security Evaluation |
| 内部结论是否可信？ | Third-party Evaluation |
| 能力是否值得部署？ | Cost Efficiency |

### 9.3 关键认知

评估不是「跑完 benchmark 就完了」— 内部 eval 频繁迭代以指引下一次训练的数据和算法方向。**评估体系是连接「当前模型表现」和「下次迭代目标」的反馈回路**。同时，K3 的评估体系展示了完整度：公开 40+、内部 20+、第三方多家独立验证、网络安全专项 — 这种组合提供了单靠任何一个维度都无法得到的完整画像。

第 6 部分与前面各层的关系如下：

| 前面章节 | 评估如何承接 |
|---|---|
| **架构** | 验证 KDA 长上下文、Stable LatentMoE 的代码/Agent 能力、MoonViT-V2 的视觉能力是否兑现 |
| **预训练** | GPQA、HLE、视觉与长上下文任务检验预训练数据和架构是否形成基础能力 |
| **Post-Training** | Coding、Agentic、工具增强和多 reasoning effort 评估 RL / MOPD 是否把能力写入模型 |
| **Infra** | 长程 Agent、1M context、复杂 harness 和 cost-per-task 评估基础设施是否真正支撑能力 |
| **部署** | Score vs. cost、工具和 cache 配置决定能力是否能以可接受成本交付 |
| **安全** | Cyber Tier 1/2、Agent Behavior、reward hacking 相关评估界定发布边界 |

因此第 6 部分不是全篇最后“报成绩”，而是前五部分的验证层：

```text
架构提出能力假设
训练把能力写入模型
Infra 让能力可以运行
评估验证能力是否真实、可靠、可部署
```

### 9.4 三个最重要的判断

#### 判断一：评估的核心不是排名，而是可解释的能力画像

总榜排名无法告诉你：

- 模型是否真的擅长长程 Agent；
- 代码结果是否依赖特定 harness；
- 视觉能力是否依赖 Python tool；
- 为什么 research-level reasoning 仍然失败；
- Agent 是结果不对，还是过程低效。

K3 用四大能力轴、内部工作流、行为评分和安全专项，把一个总分拆成可行动的能力结构。

#### 判断二：内部评估比公开榜单更接近训练方向盘

公开 benchmark 的价值是对外可比；内部 benchmark 的价值是：

```text
高频刷新
→ 跟踪 failure modes
→ 直接改数据、reward、harness 和训练
```

评估体系是模型开发的反馈控制器，而不是最终验收表。

#### 判断三：最终目标是能力—成本—风险的可行解

完整产品目标更接近：

$$
\text{Utility}
=
f(\text{Capability},\text{Reliability},\text{Safety},\text{Cost})
$$

```text
能力高但成本不可接受 → 无法大规模部署
能力高但行为不稳定 → 用户体验差
能力高但安全边界不清 → 发布风险高
成本低但能力不足 → 没有产品价值
```

### 9.5 最短记忆版

> **K3 §6 不是“跑了多少 benchmark”，而是用公开榜单建立能力地图，用内部评估定位 failure modes，用网络安全评估划定风险边界，用第三方评估降低自测偏差，最后用 score–cost frontier 判断这些能力是否值得部署。**

## 10. 安全与对齐

公开报告中安全意识层面的细节相对有限，但几个关键信号值得关注。

### 10.1 K3 体现

| 子项 | 具体做法 |
|---|---|
| **网络安全** | 主动评估 Tier 1 (漏洞发现，覆盖 Linux kernel, databases, AI services, web frameworks, blockchain, VPN) 和 Tier 2 (漏洞利用，36 tasks)；接受第三方 (UK AISI/NIST CAISI) 独立评估 |
| **Reward Hacking 防御** | Kernel 任务 hacking 检测系统 (检测 CUDA graph replay, input caching, precision reduction 等策略，持续扩展新规则)；AET 中用 hidden verifier 评估 held-out 场景 + penalty-based rewards under limited submission budgets |
| **量化感知训练** | MXFP4/MXFP8 QAT 从 SFT 开始贯穿整个后训练，不是训练完再加的「后处理」 |
| **Agent Behavior 评估** | Agent Behavior Bench 不仅评结果正确性，还评 tool-use 行为、效率和纪律 — 这实际上是安全的对齐评估 |
| **沙箱隔离** | AgentENV microVM 基于 Firecracker 的强隔离，既是为了性能 (pause/resume)，也是为了安全 — 防止 agent 的恶意操作影响宿主机 |

### 10.2 未公开部分

多语言安全、有害内容过滤、refusal 训练策略、越狱防御 — 公开 tech report 中未涉及，但这不代表没有。

### 10.3 与其他层的关系

| 与哪层的关系 | 具体体现 |
|---|---|
| 安全 ↔ 训练范式 | Reward hacking 防御是 RL reward design 的一部分；安全评估暴露的问题会驱动 RL 的 reward 修正 |
| 安全 ↔ 基础设施 | AgentENV 的 microVM 隔离同时服务于性能 (pause/resume) 和安全 (sandbox isolation)；两者在设计层面耦合 |
| 安全 ↔ 评估 | 网络安全专项评估和安全对齐评估是评估体系的子集，但独立于 benchmark 指标 |
| 安全 → 产品 | 安全评估结果影响模型是否适合公开发布、是否需要 cyberguard / refusal 等保护措施 |

### 10.4 关键认知

**安全不是训练完再加的「过滤器」**，而是贯穿评估和训练的持续过程。AgentENV 中的 microVM 隔离既优化了训练效率，也防范了 agent 误操作 — **性能优化和安全防护在这个维度上不是 trade-off，而是协同**。Reward hacking 防御体系持续演进的事实也说明：安全是一个动态博弈，不是一个一次性工程。

## 11. 部署与服务

技术报告 §5.4 详细覆盖了推理引擎层，但一个面向数百万用户的产品服务还有更多层面。

### 11.1 推理引擎层

| 子项 | K3 具体做法 |
|---|---|
| **混合架构缓存** | KDA-aware prefix cache: 统一 KDA state 和 MLA KV cache 的 paged pool；前缀哈希细化为 512-token hash block (vs 物理 6144-token block)；双阶段 lookup (MLA 匹配 → KDA checkpoint 验证)；concurrent scheduling 下的三阶段一致性保证 |
| **推理 Kernel** | KDA decoding: 缓存投影输入而非 state (与 ReplaySSM 同类设计), on-chip 重建 + 单 kernel 融合；Block AttnRes: inter-block 在 side stream 执行, intra-block 融合进 TP all-reduce；Stable LatentMoE: latent projection 与 MoE router 融合 GEMM, WarpDecode token-centric kernel |
| **量化部署** | MoE expert 权重 MXFP4, 激活 MXFP8；非 MoE 模块 (attention, latent MoE projections, shared experts, routers) 保持高精度 |
| **投机解码** | MTP layer → EAGLE-3 draft model, 训练阶段直接优化 $L_{\text{LK}}$ (acceptance rate) 而非 KL-divergence |

### 11.2 调度系统层

| 子项 | K3 具体做法 |
|---|---|
| **Service Discovery** | Cache-aware affinity scheduling: consistent hashing 将每 session 绑定到两个集群 (primary + hot standby)，保持 cache locality 同时限制故障影响范围 |
| **Admission Control** | Budget-based admission control: 为短请求和长请求分配独立资源预算，防止 bursty 长上下文流量挤占短请求 |


### 11.3 产品层

| 子项 | K3 具体做法 |
|---|---|
| **Kimi Chat** | 面向普通用户的多模态对话产品 |
| **Kimi Code** | 面向开发者的 coding agent CLI 工具 |
| **开发者 API** | 面向企业和开发者的 API 服务 |

### 11.4 与其他层的关系

| 与哪层的关系 | 具体体现 |
|---|---|
| 部署 ↔ 架构 | KDA prefix cache 的物理块大小 (6144 tokens) 和 hash block (512 tokens) 的分离是由 KDA checkpoint 的稀疏性和 MLA 的细粒度共同决定的 — 架构特征直接定义了缓存的可能形状 |
| 部署 ↔ 训练范式 | 投机解码的 draft model 是从训练的 MTP layer fine-tune 而来；MXFP4 量化在 SFT 阶段就开始适应 |
| 部署 ↔ 评估 | 成本效率评估 (score vs $/task) 直接量化部署优化的效果 |
| 部署 → 产品 | TTFT, 吞吐, 长上下文响应延迟, 多模态输入延迟 — 这些是用户体验的核心指标，由部署层决定 |

### 11.5 关键认知

部署层的优化直接决定用户体验和商业可行性。K3 的推理成本比 Fable 5 低 1/3~1/10 — 这个优势虽在评估中通过 benchmark 体现，但**源头在部署层的每一项优化**。Deployment-aware post-training (§4.1.4) — 从 SFT 起就量化训练、draft model 直接优化 acceptance rate — 意味着部署不是训练后的适配，而是从训练开始就参与的决策。

## 14. 全体系总结

三层核心技术栈 (架构、训练范式、基础设施) 定义了模型的**能力边界**，五层外围体系决定了模型的**可用性**：

| 层 | 回答的核心问题 | K3 最亮眼的东西 |
|---|---|---|
| 数据工程 | 喂了什么知识 | 全领域覆盖 + 合成长上下文 |
| 模型架构 | 理论上限在哪 | KDA + AttnRes + Stable LatentMoE 三合一 |
| 训练范式 | 怎么练出这些能力 | 3×3 RL + MOPD 蒸馏 + AgentENV 环境 |
| 基础设施 | 能不能规模化跑起来 | MoonEP 完美负载均衡 + KCP + 1M RL co-located |
| 评估体系 | 到底有多强 | 40+ 公开 + 20+ 内部 + 4 家第三方 |
| 安全与对齐 | 能不能安全放出去 | 自主发现 16 个 Zero-Day + 第三方审计 |
| 部署与服务 | 用户能用得起吗 | 成本低 1/3~1/10 + EAGLE-3 加速 + cache-aware 调度 |
| 生态与迭代 | 能持续多久 | 权重+论文+代码全开 + 季度发布节奏 |

**最常被低估的是数据工程和评估体系** — 前者决定知识面和能力边界，后者是整个开发循环的「方向盘」。而**安全和部署则决定一个模型是论文里的数字还是用户手里真正可用的产品**。

K3 之所以特别，不是因为在某一层做得极强，而是因为**七层同步推进到前沿** — 这在开源模型中前所未有。
